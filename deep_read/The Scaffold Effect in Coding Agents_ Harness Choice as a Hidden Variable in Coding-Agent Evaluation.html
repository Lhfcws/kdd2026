The Scaffold Effect in Coding Agents
Harness Choice as a Hidden Variable in Coding-Agent Evaluation - 深度精读

标题：The Scaffold Effect in Coding Agents: Harness Choice as a Hidden Variable in Coding-Agent Evaluation

作者 / 机构：Naman Vats, Oleg Golev（Sentient Labs）

来源：arXiv 预印本（2026）；代码与数据 github.com/namanvats/scaffold-effects

领域 / 任务：Agent 评估 / 编程智能体（coding agent）基准测试与成本评测

一句话论文：在固定模型、仅改变 harness（脚手架/运行框架）的受控实验下，harness 选择带来最高 40x 的每解决任务 token 差异，却只带来 0-8pp 的通过率差异；据此主张编码 agent 评估的比较单位应为 harness-model pair。

标签：agent 评估harness / scaffoldtoken 效率失败模式分析人本位评测Terminal-Bench Pro

阅读决策：精读 理由：结论对「如何公平比较编程 agent / 如何读排行榜」有直接的工程指导意义；实验设计干净（受控变量、bootstrap 不确定性、失败指纹复现），适合做论证链拆解与批判审查。n=50、2 模型 3 harness 限制了外推，需在批判节显式标注。

整体认知

问题（Problem）

公开编程智能体排行榜通常按模型名 + 通过率排名，而模型外围的 harness / scaffold——即下发工具、管理上下文、决定何时停止的运行框架——经常被含糊处理（不公开、为刷分而变动、或隐式当作受控常量）。作者指出的核心张力是：仅当 harness 固定时，模型间比较才成立；一旦 harness 变化，性能与效率就混淆了「模型效应」与「脚手架效应」。并且从「人本位」视角看，开发者真正关心的是每任务成本、完成时延与监督负担，而这些都无法从一个 model-only 的分数中还原。

先前局限（Prior limitation）

SWE-bench 等基准把 scaffold 选择视为「要控制的混淆变量」，而非「值得研究的现象」。Terminal-Bench 2.0 论文已报告过线索：Claude Opus 4.5 在两种 harness 下分别为 52.1% 与 57.8%，但输入 token 消耗 256.9M vs 3.9M（65x 差异换来 5.7pp 增益）。这类观察散落各处，缺乏在固定模型、系统化改变 harness 的受控量化研究。

核心思想（Core idea）

把「仅固定模型、改变 harness」做成一个受控实验，将 harness 提升为被显式控制的自变量，并引入人本位指标（tokens/solved、no-action turns、失败类别向量）。若 harness 造成的成本差异量级远大于模型升级带来的差异，那么「模型名」就不是一个完整的比较单位。

主要贡献（Contributions）

  1. 300 次 trial（3 harness x 2 模型 x 50 任务）上测得 40x 的 tokens/solved 差距，而配对通过率差异仅 0-8pp（95% 配对 bootstrap CI 除最大差外均含 0）。
  2. harness 专属的失败模式指纹在两个模型上复现，证明它是 scaffold 属性而非模型属性。
  3. 提出以 no-action turns（既不改文件也不发命令的回合）作为成本差距的机理性代理，并将其刻画为「人需吸收的每任务监督税」。
  4. 主张人本位编码 agent 评估的单位应是 harness-model pair，并开源配置、原始日志与分析脚本。

主要证据（Main evidence）

证据以「成本侧」最稳健：tokens/solved 排序在两模型上一致为 Goose << OpenHands-SDK < OpenCode，OpenCode 约为 Goose 的 40x；bootstrap 显示 Goose 上限（40-61K）远低于 OpenCode 下限（733K-1.01M），量级差稳健。no-action turns 的 10x 差异跨模型复现。失败指纹（Goose=REASON、OpenHands=VERIFY+MAX_TURNS、OpenCode=TIME+空转）跨模型一致。相比之下，通过率差异（0-8pp）在 n=50 下基本落在 bootstrap 噪声内，属描述性而非统计确证。

方法

实验设计：受控变量法

研究在 Terminal-Bench Pro 的 50 个任务（跨 8 类原型 stratified 抽样、pytest 确定性评测）上，对两个近期强编码模型 Qwen 3.6 Plus 与 MiniMax M2.5，跨 3 个开源 harness，共 300 次 trial。设计的关键在于「什么被固定、什么被研究」：

  • 固定（held constant）：逐字原始任务说明、原生测试套件、Daytona 沙箱、900 秒墙钟上限、OpenRouter 网关、基本相同的 system prompt（同一套操作原则 + 四技能 playbook）。
  • 不固定（即研究对象）：各 harness 的原生工具 API、自动上下文预加载、内部重试 / 子智能体逻辑。
  • 刻意不拉平：暴露的预算控制（turn-budget）是 scaffold 的一部分而非干扰项——Goose 与 OpenHands-SDK 传 40-turn 上限；OpenCode 经 Harbor 不暴露 turn-budget 标志，仅受墙钟约束。
flowchart TD A[固定模型] --> B{{仅改变 harness}} B --> G[Goose: 重 IDE 预注入文件树] B --> O[OpenCode: 持久工具循环-无自动预加载] B --> H[OpenHands-SDK: 微智能体-子智能体委派+显式验证] G --> R[300 trials: 3 x 2 x 50] O --> R H --> R R --> M[指标: solved / turns / tokens_total / no-action turns / wall_seconds / 6类失败] M --> C[成本侧: tokens per solved task] M --> P[精度侧: pass rate] M --> F[行为侧: failure fingerprint + no-action turns]

三个 harness 的脚手架哲学

Harness脚手架哲学失败指纹
Goose重型 IDE agent，激进文件树预注入REASON 主导，零 VERIFY（卡住即停）
OpenHands-SDK微智能体架构，子智能体委派 + 内部重试 + 显式验证VERIFY + MAX_TURNS
OpenCode持久工具循环，无自动上下文预加载TIME + 空转（idle spinning），零 VERIFY

指标与 token 记账

每个 trial 收集：solved、turns_used、tokens_total、avg_no_action_turns（既未改文件也未发命令的回合，作为监督负担代理）、hit_turn_budget_count、wall_seconds，以及事后 6 类失败分类（REASON/VERIFY/TIME/MAX_TURNS/HANG/ERROR，决策树见附录 A）。

tokens/solved 按「调用方计费口径」摊销：单元格内所有 trial 的 tokens_total 之和 除以 该单元格已解决任务数，即失败与基础设施错误 trial 的 token 也计入分子。公式：

$$\frac{\sum_{t\in\text{cell}} \text{tokens\_total}_t}{|\{t:\text{solved}_t\}|}$$

作者刻意不跨供应商归一化：因为 harness 报告的 token 数才是部署相关的量。token 来源有分层回退——OpenCode / OpenHands 用 harness 发出的 ATIF 总量（含 in/out 拆分）；Goose 经 Harbor 只能拿到 total-only 字段（无输入/输出拆分）。bootstrap 不确定性用 95% 配对任务 bootstrap 区间（B=10,000）报告。

Figure 1：Pareto 前沿（通过率 vs. tokens/solved）

读图要点：6 个点（3 harness x 2 模型）中，Goose 两点位于左上角（低成本、中通过率），没有任何点在「同等或更高通过率下成本更低」意义上支配它；OpenCode 两点被 Goose（成本更低、通过率相当）与 OpenHands-SDK（成本更低、通过率相同）双重支配。这可视化地支撑了「成本侧差异压倒精度侧差异」。

Figure 2：no-action turns（每任务平均）

OpenCode 平均 2.0-2.16 个 no-action turns/任务，是 Goose（0.2-0.3）的约 10x，跨模型复现。每个 no-action turn 因消息历史累积而承载整段上下文的输入 token，故在平均位置 ~10 与 ~20 的两个空转会浪费数千 token——作者称之为「每任务 idle-turn 税」。

失败模式指纹（跨模型复现）

三类指纹在两模型上稳定出现：Goose 为 REASON 主导（卡住即诚实放弃、零 VERIFY）；OpenHands-SDK 为 VERIFY + MAX_TURNS（倾向提交似是而非的错误补丁或耗尽迭代）；OpenCode 为 TIME + 空转（更常耗尽墙钟，但因其零 VERIFY，命中测试的解更可信）。这一复现性被用来论证指纹是 scaffold 属性 而非模型属性。

批判评价

优点

  • 受控变量干净：固定任务/sandbox/墙钟/prompt，唯一自变是 harness，使「harness 是隐藏混淆变量」可被直接量化，而非停留在修辞。
  • 成本侧证据稳健：tokens/solved 的 40x 与 no-action turns 的 10x 在双模型上一致，且 bootstrap 区间不重叠，量级差可信。
  • 失败指纹的复现设计：跨模型一致性强，且给出决策树（附录 A）与 20% 人工复核，提升可审计性。
  • 人本位指标创新：把成本、时延、监督负担纳入评估，直击「排行榜分数!=可部署性」的痛点。
  • 透明度高：开源配置、日志、脚本与 50 个任务 ID，可复现与二次评估成本低。

不足 / 风险

  • turn-budget 不对称污染 40x：Goose/OpenHands 有 40-turn 上限，OpenCode 仅受 900s 墙钟约束（实测最长 67-69 turn）。作者用「88%/71% 在 40 turn 内」辩护，但 gap 的真正来源（per-turn token 体积）从未逐项归因。
  • token 记账口径不一：Goose 只报 total（无 in/out 拆分），且各 harness 对子智能体委派、内部重试、工具序列化的计数方式不同。40x 可能部分来自测量工具差异而非纯 scaffold 效率。
  • 失败指纹与 instrumentation 纠缠：分类树依赖 harness 专属字段，OpenCode 永不产生 MAX_TURNS；故「指纹=scaffold 属性」的论证中混入了一部分框架人造差异。
  • 统计功效低：n=50 使通过率效应基本在噪声内，精度侧结论只能是描述性的。
  • 泛化受限：仅 2 模型、3 harness、全经 OpenRouter 默认采样；结论不应外推到未评估的闭源商业产品或所有脚手架架构。
  • 机制未拆解：研究把 harness 当作「一束差异」整体隔离，证明 harness 重要，却无法指出是上下文预加载、子智能体、还是重试逻辑中的哪一个驱动了 40x。

隐含假设（Hidden assumptions）

  • 「harness 报告的 token 数 = 部署相关成本」——忽略不同 harness 对 cached token、prompt 模板、内部调用计费的口径差异。
  • 「no-action turn 对人是负担」——假设 reviewer 必须阅读这些回合，未实测人类实际开销。
  • 「turn」是跨 harness 可比的单位——但 turn 的 harness 定义不同，可能包含不同数量的内部 LLM 调用。
  • OpenRouter 默认采样（温度/top_p/max_tokens/路由）在运行间稳定——作者承认可能漂移，精确复现需固定。

复现风险（Reproducibility risks）

  • Provider 默认与模型版本随时可变；run metadata 记录了当时设置，但是「软」复现约束。
  • Goose 的 token total-only 字段使 per-direction 对比不可得，削弱细粒度复现。
  • 50 任务由 GPT-4o-mini 分类后 stratified 抽样，分类噪声可能影响类别层面结论（IMPL 等）。

最值得注意的 1 个批判点

论文最亮眼的 40x 数字同时被两个不对称污染：①OpenCode 没有 40-turn 上限、仅受墙钟约束，而 Goose/OpenHands 受上限；②各 harness 的 token 记账口径不同（Goose 连 in/out 拆分都没有，且 OpenHands/OpenCode 把子智能体委派与内部重试计进 token）。作者虽用「88%/71% 在 40 turn 内」部分辩护，但从未把 40x 拆成「上下文增长 / 工具序列化 / 记账口径」各自贡献多少。因此「40x scaffold 效率差」应读作带测量框架溢出的上界估计，而非纯 scaffold 行为效率差——这并不推翻核心论点（harness 是隐藏变量、成本侧差异压倒模型升级），但削弱了把它当作精确数量宣称的可靠性。

研究用途

可复用的设计

  • 受控变量协议：比较 agent 时固定任务/sandbox/墙钟/prompt，仅放开 harness，是评估「系统 vs 模型」贡献的干净范式，可直接套用到其它 agent 基准。
  • 人本位指标三件套：tokens/solved、no-action turns、失败类别向量——比单一 pass-rate 更能反映可部署性，适合加入任何 agent 排行榜。
  • 失败分类决策树（附录 A）：exception-first 的 6 类 taxonomy 可直接复用作 agent 失败归因的标注规范。
  • harness-model pair 作为比较单位：选型/评测时显式报告 pair，避免跨 harness 分数不可比。

应规避的设计

  • 只报 pass-rate + 模型名，不报 harness 规格与成本——论文证明这会把成本侧两个数量级的差异完全隐藏。
  • 把 harness 当「要压掉的混淆项」而非「要研究的自变量」——SWE-bench 式做法掩盖了部署相关信息。
  • 跨 harness 直接比较 raw token 数而不说明记账口径——易产生伪差异。

后续论文 / 研究方向

  • 该文引用的基准与方法：Terminal-Bench 2.0 (arXiv:2601.11868)、Terminal-Bench Pro（Alibaba）、SWE-bench (arXiv:2310.06770)、OpenHands SDK (arXiv:2511.03690)、Harbor 框架。
  • 可做的 idea：① 在统一 turn-budget + 统一 token 记账下重测 40x 是否收敛，拆出各机制贡献（消融式 harness 研究）；② 把 no-action turns 与真实人类 reviewer 成本做相关实验；③ 扩大模型/任务数做 harness x 模型 的交互效应分析；④ 设计「harness-agnostic」的失败标注，剥离 instrumentation 造成的指纹差异。
