# Evaluating Enterprise Analytics Agents: An End-to-End, Trace-Backed Methodology

## 背景与 Idea
企业分析 agent（analytics agent）不只是 text-to-SQL 系统。它要解读业务意图、选择指标定义、挑选数据源、执行工具、检视结果，并产出自然语言答案；这些答案可能影响运营、财务乃至高管决策。正因如此，传统"最终答案是否正确"的评估不足以诊断失败根因：一个看似合理的答案可能用了错误的真相来源（source of truth）表、跳过了必需的分解步骤、在没有支撑的情况下声称因果、或在重复运行间悄悄改变了表格解读。一个典型例子是：某 finance 问题要求做同比季度收入对比，agent 选了一张看似合理的收入表、头条数字与金标准仅差约 0.3%，但没用规定的真相表、也没做"按项目分解收入"的必需步骤——最终答案评分器会因为它数字接近而给高分，而端到端评分器会因它跳过方法而标为不完整。本文把评估问题定义为比 SQL 准确率更宽的东西——SQL 正确是必要的，却不充分；可信的分析 agent 评估必须检查"答案是怎么产生的"，包括是否遵循了预期的分析方法、重复运行是否给出稳定解读。作者提出一个端到端、trace-backed（轨迹回溯）的方法论，覆盖语义理解、执行质量、可靠性三类信号族，强调保留并回溯完整的运行时轨迹以把失败定位到具体阶段，而非只看最终答案。文中把"决策级（decision-grade）"狭义地定义为：评估应表明一个 agent 答案是否可靠到足以支撑某项业务决策，以及该 agent 应作答、弃权、升级还是转人工复核；方法论是治理的"测量基础"而非治理本身。

之所以不能只看最终答案，根本原因在于企业分析的答案带有"决策后果"：一个被采纳的错误数字可能直接驱动预算调整或高管决策，而它的错误往往不在最终数字本身，而在支撑数字的"分析契约"被违反。例如同样回答"收入下降了 5%"，一条用错真相表、跳过少交税项目分解的轨迹，与一条严格遵循规范方法的轨迹，在最终答案评分器眼里可能得分相近，但在领域专家眼里可靠性天差地别。论文把这种"数字接近但方法错误"的情形称为正确数字、错误分析契约（correct number, wrong analytical contract），并把它列为端到端评估要抓的核心失败类型。

## 核心方法
方法论首先区分四个专家评审维度，并映射到三族信号。问题解读（question interpretation）检查 agent 是否理解指标、范围、时间窗、细分与决策上下文；SQL 与数据溯源（SQL and data sourcing）检查是否用了正确表、连接、过滤、粒度与计算；洞察推理（insight reasoning）检查是否解释了结果、分解了驱动因素、避免了无支撑的因果声称；输出质量（output quality）检查答案是否完整、可读、有保留、对用户有用。其中问题解读 + SQL/数据溯源构成"语义理解（semantic understanding）"，洞察推理 + 输出质量构成"执行质量（execution quality）"，而跨运行的可重复性（repeatability）单独构成"可靠性（reliability）"。这引出三条评估要求：其一，轨迹感知（trajectory-aware）——工具使用失败在最终答案里常不可见（可能用对工具但参数错、跳过前置查询、在 schema 发现上死循环、弱证据下不升级）；其二，分析专用（analytics-specific）——通用轨迹检查不知道某张表是否 canonical（规范）、某指标是否有本地定义或必需过滤，必须把通用工具失败映射到领域失败（错源、错粒度、错时间窗、缺分解、无支撑指引）；其三，可重复性（repeatability）——单次成功不代表可靠，若同一问题在不同运行产生不同表/数/结论，会制造虚假稳定感，对预测、异常解释、实验复盘、高管报告等高风险问题尤其重要。

方法论分三阶段运行。第一，构建具代表性的问题库（按业务域、问题类型、数据源层级、歧义度、决策风险打标签，避免把探索性趋势题与高精度的财务/预测题混成一个总分），配人工撰写的"金标准答案"（golden answer），并在隔离、随机化、重复试运行中捕获运行时轨迹。金标准答案不止是最终答案，而是领域专家期望工作流的紧凑描述：可含必需来源、禁止来源、日期窗、过滤、分解步骤、数值区间、期望术语，以及答案不得做出的声称；案例研究中每条金标准由该业务域负责专家起草、并由第二名分析师独立评审批准，带"草稿/已批准"状态标记（但未计算正式评分者间一致性）。第二，每次运行先过运行有效性检查（run-validity check），排除断裂的执行环境被误判为 agent 行为（如基础设施鉴权失败、缺真实数据），再接受分级打分：把主信号（primary，评估核心分析契约）与诊断信号（diagnostic，解释主结果为何变化）分开，并把"弃权（abstention）"作为一等公民 verdict。每个打分器返回四种 verdict 之一：yes / partial / no / unknown，其中 unknown 是显式弃权而非失败；聚合时 unknown 从分母剔除并单独报覆盖率，已判定运行中 yes=1.0、partial=0.5、no=0.0，通过率即这些分数的均值。这种"未知即弃权"的设计便于暴露金标准缺失与范围外问题，避免把缺失误算成失败。第三，分数喂入一个决策框架而非发布闸门——它让失败可见、可行动，但确切阈值须经领域专家校准后才成为阻断性上线标准，故论文称其为"决策框架"而非"已验证的发布策略"。

核心机制是 runtime trace capture（运行时轨迹捕获）：每次运行记录原始问题、配置元数据、工具调用、查询文本、查询输出、错误、重试、延迟、工具轮数（tool-round count）与最终答案；轨迹是中心证据对象，一旦结果错误即可定位到解读、源选择、SQL 构建、工具失败、结果解读或最终合成中的某一环。基于这些轨迹，论文给出一个分析专用失败分类法（failure taxonomy），把通用轨迹失败映射到具体数据/决策风险（如错真相表→加 source 层级与规范路由，错时间窗→加 schema 校验，无支撑因果→加备选假设检查与升级闸门，跨运行不稳→加重复运行检查与确定性规划），并总结出企业落地所需的五个治理原语：运行时轨迹可追踪性、弃权与升级、主信号 vs 诊断信号的分层、隔离重复运行带来的运行稳定性、以及基于轨迹契约的版本比较。论文强调：语义上下文（metric 词典、source 层级、规范查询）只能告诉模型"好行为长什么样"，工作流强制（workflow enforcement）才能阻止模型跳过必需步骤，而轨迹评估验证这些步骤是否真的发生——三者缺一不可。

这一"语义上下文 + 工作流强制 + 轨迹评估"的三角，恰好对应企业落地时的三个投入层次：建指标词典与真相表层级是数据治理，写工作流强制（必需步骤、校验、升级闸门）是工程改造，而轨迹评估是验收手段。论文的启发是，若只做语义上下文（很多企业的"知识库增强"止步于此），agent 仍可能访问了定义却不遵守步骤；必须把"步骤是否发生"变成可验证、可测试的对象，而这正是 trace-backed 评分的用武之地。失败分类法还把每个通用工具失败映射到具体修复目标，使工程团队拿到评估结果后知道该改提示、改工具、改工作流还是改审查策略，而不是只得到一个模糊的低分。

## Performance 概括
Reasoning 配置将 early refusal（过早拒绝）从 73% 降至 0%，real-data 使用率从 21% 升至 73%；但 16% 的 trace 触及 tool-round 上限（执行超步），且 41/50 个问题在不同运行间改变了表格解释（跨运行不一致）。Finance 子集 30 条 trace 中，27/30 至少违反一项 contract check，显示可靠性问题显著。补充细节：Reasoning 配置平均延迟 119s（p90 234s）远高于 Fast 的 41s（p90 86s），schema 探查超限率高达 77%；Finance 结构化金标准上，Reasoning 把 required table used 从 0% 提至 50%、escalation 从 29% 提至 93%，但 decomposition method 仅从 3% 微升到 10%、canonical 分解仍弱；契约违反主要来自非规范真相表（15/30）与跳过分解（27/30）。轨迹层风险上，Reasoning 的不合理数值声称（10.7%）与硬矛盾（7.3%）反而高于 Fast（2.0%、5.3%），说明"答得更多"未必"更可靠"。这些数据说明若只按最终答案打分，会把 Reasoning 升级误判为无保留的胜利。

## 论文价值与不足
价值在于提供一个可操作的端到端评估框架与 trace 回溯机制，使企业能把 agent 失败根因定位到"语义/执行/可靠性"而非仅看最终答案，并用真实企业分析场景（大型在线市场）验证了"模型升级不足以消除工作流控制需求"这一要点：更强模型只是把失败面从"过早放弃"转移到"过度探索与不稳定解读"，并未自动产生规范的分析方法。其分析专用失败分类法把通用工具失败映射到领域修复目标，对治理有直接用处；五类治理原语也为企业搭建 agent 治理提供了最小组件清单。

不足有四：一是数据与 agent 均来自单一公司内部，跨公司/跨域泛化需更多验证；二是案例仅比较两种模型配置、并非完整模型基准，且 Finance 是唯一具备完整结构化金标准的业务域，其它四域金标准覆盖不足，故 Finance 评分卡属诊断证据而非完整基准；三是金标准由作者/领域专家定义、未计算正式评分者间一致性（inter-rater reliability），标准化与可复用性不足，不同企业需自建；四是跨运行不一致（41/50）提示评估本身需多次重复才能得到稳定结论，单次运行会高估可靠性，且 LLM judge 仅列为后续方向、当前证据主要靠确定性轨迹信号。

## 工业界落地可行性评估
直接面向企业分析 agent 的生产评估需求（可靠性、契约合规、失败归因），方法论可嵌入企业 LLMOps / 评估管线，作为上线前校验与回归测试组件，落地可行性高。最易落地的部分是运行时轨迹捕获与运行有效性检查——只需在 agent 执行层加埋点即可获得中心证据对象，几乎零侵入；其次是把"主信号 vs 诊断信号"分层，避免把大量诊断分数误当发布闸门；"未知即弃权"的 verdict 设计也便于暴露金标准缺失与范围外问题，利于渐进式建设。

落地障碍主要有三：一是构建带结构化金标准的问题库与失败分类法需要领域专家投入，且金标准需随指标定义/真相表层级变更而维护，初期成本高；二是跨运行一致性检查要求每个问题多次重复运行，评估成本高，但对高风险财务/预测问题不可或缺，可在低风险问题上降频以节省算力；三是论文明确把阈值与自动 judge 定为"需经专家校准后才成阻断闸门"，意味着初期仍需人工校准，LLM judge 仅列为后续方向，自动化程度有限。总体看，这是一套与现有 text-to-SQL 基准（Spider、BIRD、Spider 2.0）和轨迹基准（GAIA、tau-bench）互补、且直击企业真实痛点的评估方法论，工程上务实、可渐进采用，投入主要在专家标注与轨迹基建，而非算法创新。

对资源有限的团队，建议的渐进路线是：先上线轨迹捕获与运行有效性检查（几乎零算法成本），再用确定性轨迹信号（真实数据率、早期拒绝率、工具轮超限、跨运行一致性）做回归监控，最后才逐步补建结构化金标准与失败分类法。这样能在不一次性投入大量专家标注的前提下，先获得"失败可见、可比、可归因"的基线能力。鉴于论文案例显示更强模型只是把失败面从"过早放弃"转移到"过度探索与不稳定解读"，企业不应把模型升级当成可靠性的解药，而应把评估与治理作为配套必选项。
