# Diagnostic Knowledge Graphs: Automated Benchmark Construction and Deterministic Evaluation for Multi-Step Reasoning Agents

## 背景与 Idea
本文作者为 Amazon（Bellevue）的 Chuci Chen、Zhenyu Zhang、Xinyang Shen，发表于 KDD'26 Workshop。评估 LLM Agent 的多步诊断推理（客服工单、故障报告、临床记录）长期是开放难题。作者指出理想的诊断评测须同时满足三性质：(1) 逐步骤（per-step），即定位推理链中哪一步出错而非只看最终答案对否；(2) 确定性（deterministic），即重复评测同一样本得分完全一致，从而支撑纵向漂移监测；(3) 忠实（faithful），即与专家判断高度相关。现有方法无法同时交付三者。难点来自三个性质：多步结构（正确诊断不是单一标签而是一条"症状→原因→更深原因→根因"的因果链，需要逐层比较才能定位错误）、词汇爆炸（vocabulary explosion，没有规范化时语义相同的诊断被写成不同表面标签）、以及缺乏确定性评分（不像代码生成有测试通过/失败那样的自然精确匹配）。从已解决案例中抽取的原因标签存在极端"词汇爆炸"：仅单一症状就从 2,196 条工单中抽出 5,076 个不同 cause 字符串、92% 仅出现一次，导致 LLM-as-judge 评分存在 ±2–3pp 的轮间方差、且与专家一致性仅中等（Cohen's κ=0.60），无法支撑纵向漂移监测。本文提出核心论点：构建可复现的诊断 benchmark 与构建高效诊断 Agent 是同一个"对偶问题"（dual problem）——两者可由同一件产物解决，即一个规范化知识结构，它同时把评测的 gold standard 规范化、又把 Agent 的假设空间约束在历史原因上。知识图谱（knowledge graph）在这里指以结构化实体-关系网络组织领域知识的图，本文实例化出的 Diagnostic Knowledge Graphs（DKG）是一棵带频率先验的层次化原因树，每个节点还挂接一个经校验的 SQL 查询以连接可查询的运营数据库。作者由此论证：同一个把"词汇爆炸压平"的规范词汇，既让 benchmark 可以精确匹配，又作为推理期的"原因菜单"把 Agent 约束在历史观察到的原因上，从而同时提升评测的确定性与 Agent 的准确率。框架适用于任何“有解决轨迹+可验证数据”的域：IT 事件管理、医疗分诊、金融反欺诈、制造缺陷分析。需指出的是，DKG 的“对偶”贡献不在图谱结构本身，而在用同一份规范化词汇一次性解决“评测规范化”与“假设空间约束”两件通常被分开做的事——前者消除词汇爆炸带来的评分方差，后者把 agent 限制在历史观察到的原因上。确定性评估的生产意义值得点明：LLM-as-judge 的 ±2–3pp 轮间方差，意味着模型更新或 API 变更带来的真实性能漂移只要小于约 3pp，就会被评分噪声完全淹没、无法被监测到；DKG 的精确匹配把方差压到零，使亚 3pp 的漂移也能稳定检出，这对生产环境的回归监控至关重要。Cohen's κ 是衡量两位评分者一致性的统计量（1.00 为完全一致、0.60 属中等），论文用它说明纯 LLM judge 与专家一致性仅中等、不足以支撑纵向监控，而 DKG 规范化后把评估锚定到 92% 的专家校验准确率。

## 核心方法
DKG 是一棵有根树 G=(V, E, q, a)：节点为症状/原因/根因，边表示因果分解，q 将每节点映射到经校验的 SQL 查询（命中即 TRUE，无法验证则为 ⊥），a 将叶子映射到处置动作。其精度优先设计（precision-oriented）体现为：每个节点是单侧检测器（TRUE 才激活，FALSE 被丢弃而非用于路由），所有兄弟节点独立评估，以可恢复的假阳性为代价消除不可恢复的假阴性路由错误——这与每次分叉只走一条路的决策树不同，后者一次假阴性就会带偏整条诊断。构建分五阶段流水线。Stage 1 用 LLM（temperature 0 保证确定性）从已解决工单抽取"症状→原因链→动作"，约束原因须描述机制而非结果、剥离个案标识、动作须可复用；在 14,953 条物流工单上抽取成功率达 92%（共 1,193 条链），失败 8% 直接丢弃。Stage 2 用嵌入聚类把症状聚成诊断族：症状标签经专有 512 维嵌入模型在余弦相似度 ≥ τs 处聚类，再由 LLM 把顶层簇组织成层次树，低于 1% 频率的族被丢弃，深度由数据驱动（通常 2–4 层），最终产出 284 个症状族。Stage 2b 用两遍 BERTopic 聚类（先 HDBSCAN 出主簇、再把 30–40% 离群点用放宽密度参数二次聚类）加 LLM 合并，把成千上万表面形式压缩为规范簇（5,076→73，覆盖 97%）；LLM 合并的准则非常严格——两个簇只有在"描述同一原因且导致同一处置动作"时才合并（例如 "barcode unscanned at intake" ≡ "manual entry required because barcode unreadable"，零词元重叠却同根因），从而抓住那些共享零词元却收敛到同一机制的语义重复；规范后的链式映射通过最近质心嵌入匹配 μ(k) 实现。Stage 3 以"工单即测试用例"的测试驱动思路（类比测试驱动开发：工单是测试用例，SQL 是待测代码）为每节点迭代生成并校验 SQL：先用 30 条工单做分层抽样标注真值，再经最多 7 轮精炼循环（判别式列分析→LLM 生成模板→本地 DuckDB 执行约 10ms/条→失败样例反哺），0.8 为停止过拟合的 break 阈值、0.7 为考虑标注噪声（δ≈0.08，故真实准确率 ≥0.62）的验证阈值，未达 0.7 的节点保留但不挂 SQL；节点状态分绿（SQL 已验证）、红（已知原因但无可靠数据信号）、紫（无法经 SQL 验证、需问用户）三类。Stage 4 用确定性遍历算法自顶向下执行所有节点 SQL、收集命中节点交由 LLM 一次性综合（LLM 只叙述已验证事实、不决定探索哪条分支）；Stage 5 用新工单做增量扩充，未匹配原因作为 gap 候选，经频率过滤（≥2 次出现）与 LLM triage 后至多每族每轮加 3 个新节点再回到 Stage 3。评估采用双模式：semantic-judge 模式（对照原始 gold 链、公平跨方法比较，避免给 DKG 约束的 Agent 词汇对齐优势）与 deterministic exact-match 模式（对照规范节点 ID、零方差、用于生产监控）。错误分析把覆盖率损失分解为三项可诊断误差：树缺口（gold 节点缺失）、查询错误（节点在但 SQL 错）、judge 错误，分别由不同验证门把关。

## Performance 概括
基准构建在 14,953 条物流工单上产出 284 个症状族，无需人工整理；最大族 5,076 条原始 cause 压缩到 73 个规范簇（70× 压缩、97% 覆盖），TOP 10 族平均 57× 压缩、99% 覆盖。专家校验规范化准确率达 92%（50 例中 46 正确），超过同一专家与 LLM judge 的 80% 一致率；规范化后评估确定性为零轮间方差（σ=0），而 LLM judge 在 M2 上有 ±2–3pp 方差。五条件消融（3 个有 SQL 覆盖族、共 265 条票）显示：DKG+Tree（仅原因菜单+频率先验、无 SQL）在 receiving 族达 66% action、qty 族 49%，分别贡献 +32pp 增益的 78% 与 +44pp 的 86%；DKG+SQL 在 receiving 族 action 73%，与 DKG+Tree 的置信区间重叠，预校验 SQL 仅方向性正向、在 n=100 下不显著（需要 n≈900 才有统计力）；最难的 transit 族所有方法仅 32–43% 且 CI 重叠，树结构增益收窄至 +5pp。在 semantic-judge 公平协议下，DKG 相对无结构基线带来 +32pp action-accuracy（73% vs 41%）。

## 论文价值与不足
价值在于清晰论证并实证了"评估—Agent 对偶性"：同一套规范化词汇既把 benchmark 词汇爆炸压平到精确匹配，又作为推理期菜单把 Agent 约束在历史原因上，带来 +32–44pp 的 action-accuracy 提升，且给出零方差、可纵向监控的确定性评估与逐层错误定位能力，对工业客服/IT 故障/医疗分诊有通用意义。其位置区别于 KGroot、GROVE、KG4Diagnosis 等已有知识图谱诊断工作的三点在于：DKG 自底向上从噪声工单文本构建而非策展本体；它显式处理评测问题（词汇爆炸、轮间方差）而非只关注推理；它证明了"同一产物既解 benchmark 又解 agent"的对偶性这一此前缺失的连接。不足：Agent 评估仅覆盖 6 个族（565 条票），SQL 消融只在 3 族；专家校验样本小（规范化 n=50、judge n=20）；transit 等高频分散族增益骤降，说明方法依赖频率集中；8% 的抽取失败率与嵌入模型偏差带来规范化噪声；生产监控虽在前提（92% 忠实、σ=0）上验证，但未经真实部署时间线的长期验证；SQL 仅能在约 30–43% 节点因覆盖率不足而挂上查询（其余节点 70–87% 的 SQL 准确率受数据缺口限制）。这些边界条件（由规范词汇的秩-频分布可预测）提示，该方法在以频率集中、有可查询运营库的场景最有效；此外 Stage 3 借鉴 Spider 2.0 显示企业级 schema 上 Text-to-SQL 仅约 20% 准确率，故预校验不可省略。论文一个反直觉结论是：agent 准确率的提升主要源自评测基础设施本身，而非 SQL grounding——五条件消融显示仅靠“原因菜单 + 频率先验”（无 SQL）就贡献了 +32pp 增益中的 78%、+44pp 中的 86%，预校验 SQL 在 n=100 下方向性正向却不显著（需 n≈900 才有统计力）。这说明在许多诊断场景里，约束假设空间比接入可查询数据更能直接提升 agent 表现，也提示工业界应优先投资规范化词汇与频率先验，而非一上来就铺 SQL 校验。值得补充的是，DKG 的精度优先设计以“可恢复的假阳性”换取“消除不可恢复的假阴性路由错误”——这与每次只走一条分叉的决策树不同，后者一次假阴性就带偏整条诊断，这一设计选择正是其在多步推理上优于决策树式方法的根因。

## 工业界落地可行性评估
落地可行性高且面向真实运维场景。流水线可由"已解决工单 + 运营数据库"自动构建可复现 benchmark 与 SQL-grounded 诊断 scaffold，已在内部物流客服系统实证（14,953 条工单、284 族），可直接迁移到 IT 事件管理、医疗分诊、金融反欺诈、制造缺陷分析等"有解决轨迹+可验证数据"的域。确定性精确匹配模式适合生产环境对模型更新/API 变更做小漂移监测——这正是传统 LLM judge 因 ±2–3pp 方差而做不到的亚 3pp 漂移检测区间；逐层错误分解可定位 Agent 失效环节（如 High L1+low L2 表示识别了问题族却没到具体子因，应改进 L2 级 SQL 判别）以指导改进，这种粒度还能区分"猜对"与"推理正确但最后一步出错"。落地前提是企业需具备已解决案例文本与可查询运营库，且效果在原因长尾、频率分散的场景会明显下降，需结合频率集中度的边界判断来决定是否采用；此外还需保留人工在抽取校验与根因标注上的把关，并为嵌入模型偏差带来的 8% 规范化错误率预留容错。整体是一项收益明确、与生产 MLOps 栈兼容的方案，而非仅停留在学术 benchmark。落到工程实现，企业需准备两类输入：历史已解决案例文本与可查询的运营数据库（论文用本地 DuckDB，单条 SQL 执行约 10ms，足以支撑大规模节点校验）。生产监控上，语义治理层可在每次模型更新或 API 变更后跑一遍确定性精确匹配评分，把“亚 3pp 的真实漂移”从 LLM judge 的评分噪声中分离出来；而公平比较场景下仍可切换回 semantic-judge 模式做跨方法评测。需注意嵌入模型与抽取步骤带来的 8% 规范化错误率，应在节点挂 SQL 前先做专家抽检；对 transit 等高频分散族增益骤降的现象，应结合频率集中度边界判断，避免在不适合的场景强行套用。从运维成本看，节点 SQL 校验在 DuckDB 上约 10ms/条，即便数百节点也能在秒级完成一轮全树遍历，监控开销可控；但规范化质量依赖抽取与嵌入步骤，初次构建建议先在小族上做专家抽检再全量展开，并为 8% 的抽取失败率预留补抽通道。
