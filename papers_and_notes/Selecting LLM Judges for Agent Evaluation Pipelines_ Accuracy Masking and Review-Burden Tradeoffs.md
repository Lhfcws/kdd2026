# Selecting LLM Judges for Agent Evaluation Pipelines: Accuracy Masking and Review-Burden Tradeoffs

## 背景与 Idea
在 agent 评估管线中，LLM 裁判（LLM judge）指用一个大模型对另一条 agent 轨迹（trajectory，即多步工具调用与自然语言输出的完整记录）打分，判定其是否完成任务、是否产生副作用或陷入死循环。judge 的输出往往直接决定哪些轨迹被送人工复核、被过滤、还是放行进下游，因此它本身就是评估结论的"守门人"。用 LLM 当裁判之所以流行，是因为人工标注轨迹成本高、难规模化，而 LLM 可对每个样本快速打分；但 judge 本身也会犯错，于是"选哪个 judge"就成为评估质量的关键变量。业界选 judge 时通常只看一个头条指标——任务成功率（task-success accuracy），即 judge 给的"任务是否完成"标签与专家标签一致的比例，因为多数 agent 基准都报告这个数、且跨 judge 易比较。本文的核心论点是：把任务成功率当作 judge 选择的唯一标准是不够的，作者把这种失败模式命名为 accuracy masking（准确率掩盖）——某个 judge 在任务成功率上看起来可靠，却可能在其它维度系统性地漏掉或放大某些失败，从而悄悄改写整体评估结论。

具体而言，用于部署监控的 judge 需要能检出副作用（side effect，如越权、策略违规、误操作），用于人工复核分流的 judge 要在召回率与复核量之间权衡，用于训练数据过滤的 judge 则要同时避免"静默漏判"与"误拒好样本"。这些决策对 judge 行为提出的要求各不相同，而一个在某一用途可靠的 judge，可能在另一用途失败，且这种失败在任务成功率上看不出来。作者用 AgentRewardBench（Lù 等，2025）作为测试床，它是少数同时提供任务成功、副作用、死循环（looping）三类专家标注的 agent 评估环境，使得"在任务成功率上相似、却在其它维度分化"的现象可被直接验证。正是这种多维标注的稀缺，使得论文能首次把 accuracy masking 从直觉变为可量化结论。

更深层的问题是，任务成功率之所以被默认，是因为它对"答完没有"这种二元判断容易标注、易于跨模型比较，但它天然掩盖了"答对了但过程有害"与"过程有害却仍判定任务完成"两类情形。副作用之所以关键，是因为 agent 在网页或企业系统上的一次越权点击、一次不当的数据导出，远比"任务是否标为完成"更能决定该轨迹能否上线。论文用 AgentRewardBench 同时提供的副作用与死循环标注，第一次让"同一 judge 在任务成功率上几乎无差、在行为维度上剧烈分化"这一现象被定量呈现，从而把评估管线的注意力从"排行榜准确率"拉回到"维度级错误画像"。

## 核心方法
论文先建立一个"操作型 judge 选择框架"，把六类常见管线决策映射到各自需要的 judge 性质、忽略该性质会导致的失败模式。第一，基准打分（benchmark scoring）主要看任务成功率，但论文指出任务成功率在 judge 间几乎无区分度。第二，副作用监控（side-effect monitoring）需要高副作用召回率或低假阳性负担。第三，人工复核分流（human-review triage）要在召回率与复核负担间取舍。第四，训练数据过滤需要召回率与假阳性率（FPR）平衡。第五，成本与可靠性监控要能检出死循环。第六，目标 agent 上线或升级（rollout/upgrade）要能在目标 agent 轨迹上复测。该表并非说单个 judge 解决所有决策，而是论证"为何任务成功率作为默认选择指标不充分"：不同决策要求不同 judge 性质，而其中只有一部分被榜单式准确率捕捉。

实验固定为三个被评估 agent：GPT-4o、Claude 3.7 Sonnet、Qwen-2.5-VL-72B，每个 agent 在五种 judge 条件下、三个 web 基准上都有完整轨迹覆盖。三个基准分别是 WebArena（通用网页导航）、WorkArena（企业知识工作）、VisualWebArena（带视觉的网页任务），共 318 个任务实例 × 3 个 agent = 954 条 agent-轨迹对（同一任务在三个 agent 上出现，故不应视作独立观测）。五种 judge 条件为 GPT-4o-mini、GPT-4o、Claude 3.7 Sonnet、Llama-3.3-70B、Qwen-2.5-VL；其中 Llama-3.3-70B 用无截图变体（no-screen），其余用无动作树变体（no-axtree），因此 judge 条件在"模型 + 输入配置"上不同，被当作实用的 judge 条件而非受控的纯模型对比。专家标注由 AgentRewardBench 提供，多标注者按多数投票取每轨迹每维度单一标签，平局或不确定的标签逐维度剔除。因副作用正例稀疏，论文除准确率外还报告假阴性率（FNR）与假阳性率（FPR），并用 1000 次 bootstrap 重采样给出 95% 置信区间、用 Fisher 精确检验比较错误率。

judge 的行为被归纳为几类稳定画像：高召回过度标记者（high-recall overflagger，抓到多数正例但也误标大量负例）、静默漏判者（silent misser，漏掉多数正例）、依赖目标 agent 者（agent-dependent）、以及不确定者（inconclusive）。论文还做了探索性逻辑回归，检验 judge 条件与轨迹长度能否预测副作用/死循环错误（在 GPT-4o agent 轨迹上，按步数前三分位定义"长轨迹"，用轨迹聚类的 bootstrap 重采样做显著性检验），发现长轨迹的副作用错误 odds 高出 6.02 倍、死循环错误 odds 高出 9.40 倍，说明轨迹长度可成为运营层面的升级信号。在复核负担分析上，论文对比了七种升级策略（escalation strategies）的副作用召回率与送人工复核比例，形成一组"漏检 vs 复核量"的运行点权衡，并据此把每种管线目标映射到推荐 judge 策略（例如高风险副作用监控用 GPT-4o/Llama 作筛查器、有限预算的人工分流用 Claude 3.7、目标 agent 升级前要重新审计）。

复核负担分析的核心思路是：把"送人工复核的轨迹比例"与"被捕获的副作用正例比例"画成一组权衡曲线，运营方据此在"漏检风险"与"人工成本"之间选点。例如 GPT-4o 筛查虽能把副作用召回拉到九成以上，却要复核七成以上轨迹，对人工团队是不可承受之重；而 Claude 3.7 在约两成负担下拿到四到五成召回，更适合预算有限的例行分流。多数投票则提供中间档：召回高于单 judge 但负担也更高。论文据此明确反对"选一个最好 judge"的思路，主张按管线目标分别选 judge，因为没有哪个 judge 能同时胜任监控、分流、过滤、升级等全部六种决策。

## Performance 概括
在 side-effect 类错误上，不同 judge 的准确率差异高达 45–50pp；而在 task-success 类上差异仅为 1.6–4.4pp，说明 judge 选择对副作用类评估的影响远甚于任务完成类。GPT-4o 与 Llama-3.3-70B 表现为 high-recall overflagger（高召回、过度标记）；GPT-4o-mini 是 silent misser，漏报率 FNR 达 0.64–0.77；Claude 3.7 的误判随 agent 不同而变化（agent-dependent，在 GPT-4o 轨迹上较平衡、在 Claude 与 Qwen 轨迹上转为易漏）。补充：looping 维度准确率差异为 12.6–52.5pp，同样被任务成功率掩盖；低负担筛查策略（low-burden screener）在 17–25% 复核负担下达成 41–53% 的副作用召回，而 GPT-4o 高召回策略需复核超过 70% 的轨迹；GPT-4o 筛查在各 agent 上召回最高（90.6–94.1%）但负担也最高（71.1–77.9%），Claude 3.7 在有限预算下召回—负担比最优，GPT-4o-mini 作为筛查器被 Claude 全面压制（如 GPT-4o 轨迹上 Claude 以 24.2% 负担拿到 23.5% 召回，而 GPT-4o-mini 需 24.2% 负担仅 23.5% 召回的同等水平下被超越）。

## 论文价值与不足
价值在于量化了"judge 选择本身会改变评估结论"这一被忽视的效应，给出 accuracy masking 与复核成本之间明确的权衡关系，并落到可操作的 judge 选择指南（按管线目标、复核预算、目标 agent 轨迹分布来选 judge），对评估管线设计有直接指导意义。其"六类决策映射到不同 judge 性质"的框架也便于团队自查当前 judge 是否胜任，避免被单一准确率数字误导。论文还把"轨迹长度"提升为可工程化的升级信号，是可立即采用的实用发现。

论文的另一贡献是提供了"六类决策映射到不同 judge 性质"的自查框架，使团队不必通读全文也能对照自身场景：若当前只用任务成功率选 judge，那么监控与分流两类决策实际上处于未被检查的状态。这种把抽象结论转成表格化操作指南的做法，降低了把论文落地到真实管线的认知门槛，也便于在评审会上向非技术干系人解释"为什么不能只报一个准确率数字"。

从研究生态看，论文还补上了 agent 评估领域长期缺位的一环：多数基准只报告任务成功率，导致 judge 选型被默认为"选榜单上最强的模型"，而本文证明这种默认会系统性地漏掉副作用与死循环这类高代价失败。它因此呼吁评估社区在报告 judge 结果时，至少同时给出维度级错误画像与目标 agent 上的画像稳定性，而不是用单一准确率数字掩盖 judge 之间的行为分化。这一方法论层面的呼吁，比具体哪个 judge 更好更具长期价值。

不足有四处：一是实验基于 AgentRewardBench 这一特定基准与有限 judge 集合，未给出普适的 judge 选择准则，结论依赖基准的任务分布；二是 side-effect 正例稀疏（每 agent 仅 17–32 例），画像宜作方向性而非精确估计，且稀疏正例下聚合准确率可能掩盖大量漏检；三是 Claude 3.7 等 judge 的画像会随被评估 agent 改变，故在某 agent 上审计得到的画像不能直接外推到升级后的 agent；四是 judge 条件同时混合了模型与输入配置差异，无法干净分离"模型能力"与"输入形态"的贡献，且只在三个 web agent 基准上验证，向对话、代码、工具调用等域的外推未经检验。

## 工业界落地可行性评估
高度可行且近乎即插即用。论文可直接指导生产中的 agent 评估管线设计：对高风险的副作用类失败，应优先选用 high-recall judge（GPT-4o、Llama-3.3-70B）并承受更高复核成本，或采用多数投票在召回与负担间取中；对任务完成类评估，因各 judge 差异极小，可选用更省成本的 judge（如 GPT-4o-mini）而不损失判别力；人工复核分流在预算有限时应选 Claude 3.7 这类低负担筛查器。还可把"轨迹长度"作为一个廉价的路由规则——步数超过阈值的长轨迹自动送额外复核或二级 judge，因为论文显示长轨迹的失败 odds 显著更高。

落地障碍主要是：企业需先有带专家标注（至少副作用维度）的轨迹库来标定自家 judge 画像，标注成本高；当被评估 agent 升级或替换后必须重新审计 judge 画像，否则可能沿用已失效的选型结论；此外，论文的画像是在特定 web 基准上得到的，跨业务域前应在本企业轨迹上做小规模复测。总体属于低风险、高收益的工程实践，可直接嵌入 LLMOps 评估流水线，且无需改动被评估 agent 本身，仅需调整 judge 选型与复核分流策略。

需要强调的是，论文的画像是在特定 web 基准上得到的，跨业务域前应在本企业轨迹上做小规模复测以确认 judge 画像是否迁移；同时，当被评估 agent 升级或替换后必须重新审计 judge 画像，否则可能沿用已失效的选型结论。对标注资源紧张的团队，最务实的第一步是先建立"副作用"这一稀疏但高价值维度的专家标注，再据此为监控类决策挑 high-recall judge，而非一开始就想覆盖全部维度。
