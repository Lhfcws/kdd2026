# Verifying Agents in Rubric-Graded Environments

## 背景与 Idea
随着大语言模型驱动的智能体（agent）承担越来越开放、复杂的任务，如何验证（verify）它们的产出已经成为一个独立且困难的研究问题。本文关注一类名为"按评分量规打分的智能体环境"（rubric-graded agent environment）的范式：所谓 rubric（评分量规或评分细则），是一组细粒度、以自然语言书写、但可以被客观判定的二元准则（每条准则要么"满足"要么"未满足"），用于定义什么才算正确的产出。智能体在这种环境中会拿到任务描述，并在一个结构化环境（文件系统、一组工具、外部数据接口）中行动，最终产出一份或多份交付物（deliverable），并可能通过工具调用改变环境状态（例如发出一封邮件、修改一张表格）。验证器（verifier）的任务是针对任务附带 rubric 中的每一条准则，给出"满足/未满足"的二元判定。

这类环境与"确定性可验证"的传统智能体基准形成对照。确定性基准（例如用单元测试判定的 SWE-bench、用精确匹配判定的 HotpotQA、用程序化检查判定的 WebArena）把正确性收缩为可执行的检查，交易了可验证性换取了覆盖范围、开放性和真实感。而越来越多半可验证（semi-verifiable）领域需要判断（judgment）：例如 BankerToolBench、APEX-Agents、CoreCraft、ClawBench 等基准，开始用自然语言 rubric 作为定义与刻画正确性的技术。验证这类智能体的 rollout（一次完整运行轨迹）本身就是一个难题：智能体可能产出跨多份文件的成果（比如一份 Excel 表格加一份 PowerPoint 演示），并调用有副作用的工具（比如发送邮件）；验证需要检查"邮件是否真的发出""Excel 的公式计算是否跨标签页正确传播""PPT 的图表是否与其底层数据内部一致"等多样化性质。

本文指出，验证器本身长期被低估：现有基准大多把 verifier 当作一个子问题（给 rollout 打分的手段、或给强化学习提供奖励信号的来源），而不是作为研究对象。与此同时，verifier 的设计空间极其广阔——从简单地用 LLM-as-a-judge 在轨迹上打分，到把验证器本身也做成智能体（agent-as-a-judge），后者又从工作流式（如 Archipelago）一路延伸到完全反应式（reactive）的智能体（如 ClawBench）。这种"设计空间巨大却被忽视"的现状，正是本文把 verifier 单列出来系统研究的动机。

作为研究基础，论文选用 BankerToolBench（BTB）这一投行业务环境：它包含 100 个由初级投行分析师执行的端到端分析工作流，例如折现现金流分析（DCF）、杠杆收购模型（LBO）、可比交易分析（trading comps）和并购模型（merger models）；单个任务往往是长程的（一名投行人员平均需要 5 小时）。智能体在 BTB 中拿到任务说明、一个预置文件的资料室（data room），以及一组固定工具（市场数据平台、SEC EDGAR 接口、公司档案接口、文件系统、预装 openpyxl 与 python-pptx 等库），需要产出标准办公格式的多文件交付物（.xlsx、.pptx、.docx、.pdf），并附带一份由专家撰写的、由二元加权准则组成的 rubric。这种"多文件二进制交付物 + 工具介导的环境状态"的组合，对验证器提出了跨异构工件联合推理的高要求：判定单条准则可能需要在 Excel、PPT 等多个文件之间交叉核对。

简言之，本文要回答的是：在"智能体强、但判定难"的 rubric-graded 环境中，验证器究竟需要哪些能力，又该如何设计出既准又省的验证器。它做了第一件系统性的 verifier 研究，贡献包括：构建 BankerVerifierBench（BVB）元评测数据集；提出一套从任何 rubric 语料反推验证器所需能力的通用方法学，得到九大能力分类并提炼出三条设计原则；把这些原则实现为开源验证器 Gandalf；并在 BVB 上与现有验证器对比，验证其有效性。

## 核心方法
论文的方法可以分成"建数据集—反推能力—提炼原则—做实现"四个环环相扣的步骤。

第一，构建 BankerVerifierBench（BVB）。这是首个面向 rubric-graded 智能体环境的验证器元评测数据集（meta-evaluation dataset），把以往对 LLM 裁判（LLM-as-a-judge）和智能体轨迹的元评测，扩展到了"需要检视多文件二进制交付物与工具介导环境状态"的场景。BVB 从 BTB 的任务分布中抽取 21 个任务，每个任务都附带一份由专家撰写的 rubric，rubric 中的准则为二元判定、按重要性加权，并被打上六类之一（six categories）的标签；每条 rubric 包含 47 到 286 条准则（中位数为 160），全语料共 3,204 条准则。每个任务配一条真实的智能体 rollout，记录为完整轨迹（消息、工具调用、工具响应）以及最终环境状态（含所有交付物的原生二进制格式）。每条准则的真值（ground-truth）由领域专家给出二元结论（met/unmet）：最初 6 个任务（493 条准则）由两名评审独立标注、再由资深评审给出主判定（标注者间一致率 89.5%），其余 15 个任务（2,711 条准则）由一名评审加资深主判定完成；全语料中"已满足"类别的占比为 78.7%。这种不平衡的标签分布直接影响了后文的评价指标选择（见性能章节）。

第二，提出一套"从 rubric 反推验证器能力"的通用方法学，分三阶段。阶段一"自由文本发现"：对每个 rubric 准则，让一个 LLM 结合任务简报与准则文本，产出 1 到 3 个简短的能力标签，并为每个标签写一句话理由；程序化强制三条约束——理由必须以"验证器需要……"开头并引用准则中的短语（确保是"验证器侧"视角）、标签不得出现具体运行时/库/文件格式/数据源的名称（确保"架构无关"）、标签须遵循固定词形。阶段二"规范化"：把阶段一出现的每个唯一标签做嵌入（embedding），用凝聚式聚类（agglomerative clustering）聚成 80 个细粒度微簇，再让 LLM 为每个微簇命名、给出定义、诊断信号、示例与反例；最后一个 LLM 调用把这 80 个微簇合并为规范化的能力分类，受三条硬约束限制：规范能力数量在 8 到 10 之间、没有任何单一能力覆盖超过 40% 的语料准则、每个微簇必须恰好映射到唯一一个规范能力。阶段三"封闭词表打标"：用规范分类对每个准则重新打标，每个准则输出 1 到 3 个按置信度排序的规范能力标签。整条流水线用 Gemini 3 Flash 做 LLM 调用、用 Google text-embedding-005 做嵌入。这套方法学是 verifier 侧（描述"验证器要查什么"）且架构无关的，因此可跨验证器类型与跨领域复用。

把方法应用到 BVB 的 3,204 条准则，得到九大能力（按主标签占比排序）：审计量化指标计算（audit quantitative metric calculation，23.0%，例如重算 EV/EBITDA 倍数、交易费用）、核实字面数据点准确性（15.5%）、跨组件数据关联核对（14.9%，在表格/标签页/文件之间追迹同一个数值）、核实结构性组件清单（12.1%，确认交付物包含规定的章节/文件/列）、检视视觉呈现与风格（11.6%，字体/颜色/对齐/品牌）、审计会计逻辑与惯例（7.6%，符号规则、资产负债表恒等式）、验证文档标签与元数据（6.5%，标签页名/坐标轴标题/表头是否逐字匹配规范）、审计治理与战略叙述（5.4%，必要披露是否齐备、定性主张与分析是否自洽）、验证时间顺序与序列完整性（3.3%）。在 BVB 的金融语境下这些抽象能力被具体实例化，而同一组能力标签可迁移到其他领域（例如临床工作流会把"会计逻辑与惯例"实例化为剂量与禁忌核查，生产力工作流会把它实例化为升级策略与语气规范）。

第三，把九大能力读成一份"规范"，从中浮现出三条结构性的设计原则，分别对应自然语言 rubric 在富智能体环境中的固有特征：
- 原则一 P1（反应式验证，reactive verification）：无法仅凭准则文本预测验证路径——同属一个能力的两条准则，可能需要打开不同文件、调用不同工具、以不同顺序操作，且路径数量随 rubric 规模增长。因此验证器应当是一个反应式智能体，拿到一条准则后自主决定打开哪些工件、调用哪些工具、以什么顺序进行，直到得出判定为止；这把"分发逻辑"从架构时刻（architecture-time）挪到了模型推理时刻（inference-time）。九大能力全部呈现这一模式。
- 原则二 P2（环境对齐，environment alignment）：若干能力归结为检视工件内部结构性质（公式结构、布局元数据、跨文件引用），而这些性质一旦被拍平为文本或渲染成图片就会丢失。因此验证器应当与 rollout 智能体运行在同一环境里，访问同样的文件系统、库与工具，包括领域专属的模型上下文协议（MCP，Model Context Protocol）工具。六大能力呈现此模式；由于部署到新环境时只需授予与 rollout 相同的工具权限、无需写领域专属解析器，这一原则还顺带让验证器在构造上就是领域无关的。
- 原则三 P3（领域引导，domain guidance）：若干能力需要准则文本里没有的知识，例如投行备忘录中的会计符号惯例或披露标准。每个领域都有类似惯例（临床工作流有临床规范、法律工作流有引用规则、生产力工作流有沟通规范）。因此验证器应当在部署时经由一个独立于准则文本、也独立于架构本身的专用引导通道（guidance channel）接受领域引导，引导以与架构无关的自然语言上下文形式进入。两大能力呈现此模式。

第四，在 Gandalf 中实现上述原则。Gandalf 是一个可移植的 Python 应用：它通过开源智能体框架 OpenHands SDK 实现 P1（反应式智能体）；通过"直接运行在与 rollout 智能体相同的环境、连上相同的 MCP 工具"实现 P2；通过一套配置系统接受自然语言 judge guidance 实现 P3，引导内容可以是领域专属的（如金融模型的符号惯例），但机制是领域无关的。在此之外，Gandalf 的配置还允许指定验证器智能体所用的 LLM，从而让基准设计者在准确率与成本之间权衡；它更支持"批量判定"（batching）——把多条准则放到同一次反应式会话里一起判定，以摊薄反复打开同一文件带来的开销（BTB 的 rubric 平均约 150 条准则/任务，逐条单独验证会极其昂贵）。

整体来看，论文的核心思路不是提出一个新的 agent，而是把"验证智能体产出"这一长期被当作黑盒的子问题，拆解为可分析、可分类、可原则化的对象：先用数据驱动的方法从 rubric 反推出验证器需要具备的九种能力，再把共性归纳为反应式、环境对齐、领域引导三条原则，最后用 Gandalf 一次性把这三条原则落地为一个开源、可部署、可跨领域复用的验证器。

## Performance 概括
论文以 F1 作为验证器性能主指标，并把"判定为未满足"当作正类——因为语料中大多数准则-rollout 对都是满足的（met 类占 78.7%），对少数类（unmet）的 F1 比原始准确率更有区分度。若无特别说明，Gandalf 默认以 batch size b=16、Gemini 3 Flash、开启引导与环境对齐的 MCP 工具运行。

Gandalf 在九项能力中有七项领先，并处于 Pareto 最优（即在"准确率-成本"二维上，不存在另一个验证器在两项上都更好）。最关键的结论是"验证器架构比底层模型更重要"：用任意支撑模型（backing model）的 Gandalf，都胜过用任意支撑模型的其它验证器。按成本看，最便宜的 Gandalf 配置（GPT-5.4-Nano，$42）达到 F1 0.633，反而超过最贵的基线 Archipelago 配置（GPT-5.4，$414，F1 0.538），以约十分之一的成本高出 9.5 个 F1 点。同一验证器内部，放大模型收益递减明显：Gandalf 的 F1 从 GPT-5.4-Nano 的 0.633 到 Gemini 3 Pro 的 0.664，仅 3.1 个点的跨度却伴随约 7 倍成本增长；而 Archipelago 跨度更大（0.473–0.604），说明较弱架构更依赖强模型，但即使其最优配置（Gemini 3 Pro，$422）仍不如 Gandalf 最便宜配置。Agent-as-a-Judge 与 AutoRubric 无论换什么模型都落在 F1 0.47 以下（AutoRubric 配 GPT-5.4 达 0.472，靠强模型的部分轨迹推理弥补了缺少工件访问的缺陷）。

消融实验固定 Gemini 3 Flash 为底层模型，逐一切换 P2 与 P3 以隔离其贡献：移除 P3（judge guidance）后 F1 从 0.660 降至 0.649，成本从 $64 升到 $73；移除 P2+MCP 时 F1 基本不变（0.661 vs 0.660），但成本上升约 60%（$64→$102）。这说明环境对齐与领域引导主要削减的是成本（最多省下 4 倍 token）而非错误，而架构选择的影响压倒模型选择。

跨域泛化方面，Gandalf 被放到一个内部结构不同的个人生产力环境 OpenClaw（OPC）基准上测试，在该域六个能力全部达到最优并仍然 Pareto 占优，F1 达到 0.951，超过次优验证器 7.5 个 F1 点，证明三条原则与方法不仅适用于金融、也能迁移到结构迥异的领域。

## 论文价值与不足
价值首先在于视角转换：它把"验证器"从打分的附属工具提升为值得独立系统研究的核心对象，并指出在 rubric-graded 环境中"架构远比模型更重要"这一反直觉但极具工程意义的事实。其提出的九能力分类与三原则（反应式、环境对齐、领域引导）是可操作、可迁移的方法论，不绑定特定领域或文件格式；Gandalf 作为开源实现，配合 BVB 数据集，为后续研究提供了可复用的基座。对金融、合规审核等"判定靠专家 rubric"的场景，它给出了一条低成本、可泛化、且 Pareto 占优的验证路径。

不足与边界同样清晰：其一，评测聚焦在投行域（BTB）与单一跨域（OpenClaw），医疗、法律等其它半可验证领域的通用性仍需更多证据；其二，P2/P3 的消融显示它们主要省成本而非降错误，意味着在"错误率"这个维度上三条原则的边际贡献有限，原则是否普适仍有边界；其三，验证本身依赖 LLM-as-a-judge（用 Gemini 3 Flash 做判定 LLM），存在裁判偏差风险，且 BVB 的标注虽经资深评审主判定，但 15 个任务仅单评审加主判定，标注质量不完全对称；其四，rubric 来自 BTB 这类高度结构化的办公交付物，对更开放、更主观的产出（如创意写作）是否适用尚未验证。

## 工业界落地可行性评估
落地性很强。金融与合规审核场景（投行交付物核对、监管披露检查、研报一致性审查）可直接采用 Gandalf 类验证器，替代昂贵的人工复核或纯大模型的"自己评自己"，在保持质量的同时显著降本——最便宜配置以 $42 跑完整个数据集即超过最贵基线。其"运行在与被验证智能体相同的环境、连同样的 MCP 工具"的设计，天然契合企业已有的智能体运行底座，只需授予相同工具权限即可零改动迁移到新领域，无需为每类交付物写专属解析器。对于把验证结果当作强化学习奖励信号（RLVR）的团队，Pareto 占优意味着可以在不牺牲准确率的条件下大幅压低每步验证成本。

需要注意的落地前提有三：一是验证器仍依赖一个裁判 LLM，对审美、风格等主观准则要有人类抽检兜底；二是领域引导（P3）需要企业把自身的会计/合规/披露惯例整理成自然语言引导文本，这是一次性但必要的知识工程；三是跨域泛化虽已在 OpenClaw 验证，但企业若涉及医疗、法律等强监管领域，仍建议先做小规模人工对齐再上线。总体而言，这是一篇"开源 + 原则化 + 低成本"的高可行性方案，工程杠杆率高，适合作为企业智能体评测流水线的验证层直接引入。
