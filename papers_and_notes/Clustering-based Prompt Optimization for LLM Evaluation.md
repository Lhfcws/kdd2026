# Clustering-based Prompt Optimization for LLM Evaluation

## 背景与 Idea
LLM 作为评估器（业界常称"AI 裁判"/LLM-as-judge）越来越多地替代人工，对搜索结果质量、候选可信度、agent 轨迹等任务打分，规模与成本都远超人工可负担的范围。其核心前提是：只要用一个措辞得当的评分细则（rubric，即喂给评估器的打分提示词）去提示 LLM，它就能近似人类的评判。但 rubric 极其脆弱——措辞上很小的改动就能让评估器与人工的共识（human–AI agreement，即评估器打分与人工评分者一致的程度，是此类系统唯一有意义的优化目标，因为人工才是真值来源）漂移数十个百分点。论文实验中，仅给手写 baseline（记为 v0）加一条规则，就使某任务留出集上的共识复合指标变动 +41.67 分，说明"手写 rubric"与"校准良好的 rubric"之间的差距足以决定该评估器是否可用。

问题随之而来：专家标签稀缺（论文数据为数百条"双评查询"dual-rated queries，每条由两名独立人工评分者盲标），而每一次评估调用本身又是一次昂贵的 LLM 推理。通用 prompt 优化器（如 DSPy/MIPRO、以及反思式变异优化器 GEPA）的设计假设是"评估廉价且充足"——每个候选提示都能在大量样例上低成本打分；这一前提在 evaluator-rubric 校准场景中直接被打破。作者据此把问题重新定义为"数据效率问题"：在固定训练查询与专家标签预算下，如何用最少的评估调用最大化留出集（held-out，从未参与编辑、只做一次性最终测试的查询集）上的人—AI 共识。三种被比较的方法都吃相同输入（baseline rubric、固定训练集、双人工标签）、产出相同类型输出（一个胜出 rubric、在留出集上只测一次），差别只在三个维度——分歧如何聚合（reflective minibatch / top-K 列表 / 聚类共识）、产出什么粒度的编辑（整段指令 / 打包补丁 / 每族一条原子规则）、如何筛选候选（minibatch 严格改进 / 单一训练 Δ / 噪声感知自助）。作者提出的"cluster + batch-validate"单次循环即在此框架下作为解法。这一问题的生产意义在于：搜索引擎、电商、内容平台的质量团队日常依赖 LLM 评估器驱动排名决策与质量看板，而评估器与人工共识的每一点偏差都会放大到海量流量上；因此"在小标签预算下把 rubric 校准到贴近人工"不是学术练习，而是上线前必须完成且要可审计的环节——这正解释了为何作者把"每条编辑可独立审计、可回滚"作为方法设计的硬约束，而非追求一次性最高分。

## 核心方法
论文在来自同一商业搜索垂类（非英语市场、每个任务 300 条双评查询，覆盖头/躯干/长尾查询，评测对象是生产检索流水线返回的 rank-1 候选卡片）的两个评估任务上对比三种方法。术语上，evaluator 是待测的打分 LLM，proposer 是另一直言建议 rubric 编辑的 LLM；disagreement（分歧）定义为"评估器分数同时不同于两名人工评分者"的查询；composite 是共识度量指标，定义为 exact%（精确一致率）减去 0.5×MAE×100（平均绝对误差，序数分值 0/1/2），越高越好；atomic rule（原子规则）是单条 rubric 编辑，bundled patch（打包补丁）则是多条编辑一起应用。

直觉式 linear loop 是把人调试 rubric 的过程形式化：每轮读最差分歧的 top-K 训练样例（K=30：20 最差+10 随机作回归护栏）→proposer 返回打包补丁（通常 2–4 条一起改）→人工审后应用并记录 changelog→在完整训练集上重评→仅当相对上一版 train Δ≥+0.5 才接受→所有轮结束后做一次验证选出胜者。它暴露出两个结构性缺陷：cross-step bleed（跨步渗入，改一个 rubric 步骤悄悄改变了非目标步骤的判定）与 bundled-edit attribution opacity（打包编辑无法把增益归因到单条编辑）。论文在 Vertical Candidate 上跑了 4 轮（2 接受 2 拒绝）、Vertical Quality 上 3 轮接受，正是这两个缺陷推动了"原子化 + 单步锚定"的替代设计。

自动化优化器 GEPA 跑 10–20 轮：维护候选 rubric 种群，从帕累托前沿（至少在一个训练样例上最优的候选，保留多样性而非塌缩到单一领头者）选父代，让反思 LLM 读一小批父代分歧并重写整个指令体，子代仅在同批上严格优于父代才被接纳，最终返回最高分候选。由于本论文 rubric 是单组件程序，GEPA 的逐组件粒度不可用，编辑单位退化为最粗的整段重写。

提出的 cluster loop 仅跑一次端到端：① 收集 v0 在训练集上的所有分歧（训练池小时可补充同评估器/同 rubric 捕获的查询，但绝不触碰留出集）；② 用 4–5 路并行 proposer 调用（两次输入洗牌 + 2–3 次提示重构，轴覆盖错误语义、候选位置、rubric 步骤），每路返回 3–5 个带名的失败族（failure mode），每族含声称可修复的查询与一条草稿原子规则；③ 跨运行计算成对共现，若某查询对在 N 次运行中有 (N-1)/N 次落在同一簇，则形成稳定的"共识失败族"，仅单次出现的视为 proposer 噪声丢弃；④ 每族生成"v0 + 一条锚定到正确 rubric 步骤的原子规则 + 一行跨步作用域护栏（把规则限制在其目标步骤，防止跨步渗入）"的候选变体；⑤ 并行批量校验（每变体约 5 分钟墙钟），对每变体计算 composite Δ、各维度 bleed 差、以及 200 次自助子采样的 Δ 分布；⑥ 仅当通过 Table 2 四道预注册门才接受——(a) train Δ vs v0 ≥ +0.5（过滤无操作规则），(b) bootstrap P(Δ>0) ≥ 95%（过滤采样噪声），(c) 每个非目标维度在 ±2pp 内（过滤跨步渗入），(d) 至少一个 v0 已正确的 canary（金丝雀，即 baseline 已正确打分的保留查询）仍正确（过滤对已正确查询的回归）；所有阈值在验证任何变体前固定；⑦ 只对胜出变体做单次留出测试，留出集全程不触碰、绝不作为选择信号。论文用 LLM proposer 而非 embedding 聚类，是因为每个簇自带下一步要消费的产物（草稿规则与声称可修复查询）。共识失败族的筛选是 method 的关键去噪步骤：单次 proposer 调用产出的簇常含 proposer 自身噪声（把本不相关的查询归到一起），因此作者发 4–5 路并行调用、对每对查询统计"共现于同一簇"的次数，仅当在 (N-1)/N 次运行中同簇才认定为稳定族，单运行独有的成员直接丢弃；两个数据集各得到 4–5 个族且无纯噪声分配，说明该阈值有效。四道接受门之所以"预注册"（所有阈值在验证任何变体前固定）是为了避免事后挑阈值制造假阳性——(a) 过滤无操作规则，(b) 过滤把采样噪声当增益（单种子验证会把 linear 虚高到 +10.00，正是未做噪声感知的典型陷阱），(c) 捕获跨步渗入，(d) 捕获对已正确查询的回归；其中 (c)(d) 只在 canary 覆盖范围内有效，作者明确承认同一维度上与 baseline 文本矛盾、且落在训练池代表性不足输入上的规则未被检查，是已知风险面。

## Performance 概括
在留出集单次测试中，cluster loop 是两个任务上唯一稳健为正的方法（P(Δ>0)=100%）：Vertical Candidate 上 C1 达 +6.00（v0 40.33→46.33，95% CI [+3.0,+11.5]），而 linear 仅 +0.67（P=55%）、GEPA +1.67（P=79%）；Vertical Quality 上 F3 达 +41.67（v0 33.33→75.00，CI [+16.7,+70.0]），远超 linear 的 +9.52 与 GEPA 的 +16.67。验证阶段显示单种子验证会严重误导（linear 被夸到 +10.00 的采样假象），而 8 折多种子均值排序与留出集一致：C1 多种子 +7.75±4.53、linear +1.25±3.06。成本上，一次 cluster loop 约 US$25，与 linear 全量运行相当、远低于 GEPA 的 10–20 轮，且产出更强 rubric。需注意 Vertical Quality 的有效留出配对仅 36–42 对（因 S4 可评性过滤，多数查询不可评卡片），点估计不精确，增益集中在修复 baseline 单一"vertical card 识别"定义缺陷上；两任务评分者为 H1（严格，59% 查询给满分）与 H2（宽松，82%），两人精确一致 76%、在 1 分内 97%，被当作两个独立真值源而非平均。

## 论文价值与不足
价值在于提出并实证了一条可直接落地的"配方"：一次性聚合所有分歧→每失败族发布一条具名原子规则→仅在噪声感知多种子自助检验下接受编辑；其杠杆是"一次性聚合完整错误集 + 噪声感知选择"而非迭代深度，相比 GEPA 的 10–20 轮反思变异与 linear 的 3–4 轮人工调试，迭代次数与评估预算都大幅下降，且每条原子规则可独立审计、回滚，对"标签预算吃紧下需让 LLM 裁判跟踪人工判断"的场景普遍适用。这一思路对评估器运维还有方法论外溢：它把"rubric 优化"从玄学式的反复试错，变成有统计门槛（P(Δ>0)≥95%）、有回归护栏（canary）、可逐条归责的工程活动，使评估器质量可随业务演进被持续、可控地提升，而非依赖个别专家的手感。不足：仅两个同垂类、同评估器（Codex/gpt-5.4）、重叠双分析师池的任务，外部有效性未验证；协议上同时改动三个轴（全池聚合/原子编辑/多种子选择）未做成分消融，增益无法在三者间归因；聚类只用单一 proposer（Claude Sonnet 4.6），跨 proposer 稳定性未验证；gate 不检查同一维度上与 baseline 文本的矛盾（仅 canary 缓解）；Vertical Quality 有效样本极小、增益高度集中于单一缺陷，典型增益幅度可能更接近 Candidate 的 +6.00；此外优化两个标定不同的评分者共识回避了"以谁的校准为真值"的规范性选择，部署若采用单一评分者校准即做了有用户后果的规范性决定。

## 工业界落地可行性评估
落地可行性高，且直接面向生产环境（已在某商业搜索引擎垂类的真实质量审计批次上验证）。该 loop 以"人—AI 共识"为目标、以稀缺专家标签与推理预算为约束，单元是版本化、带 changelog 的具名规则，gate 自动决定接受、人工事后审计，回滚按规则粒度进行，契合工业界搭建 human-aligned LLM 评估器的实际工作流；规则生命周期是 append-only 失败记忆记录被拒提案及诊断，避免重复提议。可迁移到任何"LLM 裁判须在小标签预算下跟踪人工判断"的场景，论文亦指出可移植到 agent trace/工具调用轨迹打分（把分歧聚类到轨迹步骤、原子规则锚定到决策点如工具选择、事实接地、终止）。落地前提是需两名以上独立标注者提供分歧信号、且评估器本身需足够强（近地板模型无信号可搜，论文已验证近地板任务 LM 完全无信号）；同时对评估器公平性、隐私、误用抗性不在本工作范围内，需在目标域另行评估。从组织流程看，cluster loop 最契合"评估器即产品"的团队：rubric 是受版本控制的工件，每次编辑带 changelog、可逐条审计与回滚，这与搜索质量团队既有的评审文化一致；其 append-only 失败记忆还能把"被拒提案及诊断"沉淀为知识库，避免重复劳动。需要提醒的是，本方法依赖两名以上独立标注者提供分歧信号——若团队只有单一评分者或评分者高度一致（分歧极少），聚类就无料可聚、方法退化为线性循环；此时应先建立双评机制再上 cluster loop。评估器本身也须足够强：论文已验证近地板（near-floor）任务 LM 完全无信号，意味着在小标签预算下应选用能力达标的大模型作 evaluator，否则优化的只是噪声。
