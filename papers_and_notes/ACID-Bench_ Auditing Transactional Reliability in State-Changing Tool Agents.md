# ACID-Bench: Auditing Transactional Reliability in State-Changing Tool Agents

## 背景与 Idea
会修改持久状态的工具型 agent（如取消订单、退货、改地址、订票）即便对话看起来“成功”，也可能在底层应用状态里留下重复写入、过期读（stale read）、部分提交（partial commit）或未充分验证的损坏。这类 agent 是“复合 AI 系统（compound AI system）”的具体形态：模型行为、提示策略、用户交互、工具接口、注入的故障与可变应用状态共同决定系统是否可靠。论文指出，许多现有基准只判“最终用户目标是否满足”，但对事务可靠性而言，任务完成是必要的、却不充分——一个工作流可能到达奖励状态，却留下重复写入、未对账的部分提交或基于过期证据做出的更新。

ACID-Bench 把“事务可靠性”单独作为评估对象，主张用确定性的故障注入（fault injection）加基于状态的评估（state-based evaluator，不依赖 LLM judge）来量化 agent 在受控事务故障下的恢复能力，从而把“任务是否成功”与“状态是否完好”分开度量。标题借用数据库领域的 ACID 概念——原子性（Atomicity，要么全做要么全不做）、一致性（Consistency，状态不被破坏）、隔离性（Isolation，并发操作互不干扰）、持久性（Durability，提交后结果可恢复）——但论文明确说明它并不是数据库 ACID 合规测试，而是借用这一词汇作为可靠性透镜。具体映射是：原子性对应多步写入中部分提交后的补偿（compensation）；一致性与重试幂等性（idempotency，即重试不产生重复副作用）对应在重试歧义写入前先做状态检查；隔离性对应在依赖写入前刷新状态；持久性对应在上下文丢失后从持久状态恢复并验证终态。这些是不同的契约，不是可互换的标签。故障注入本身是经典的可靠性工程手段（Hsueh 等 1997），论文的思路是：任务是否成功会高估有状态 agent 的可靠性，除非把故障暴露、事务完整性、安全交接（safe handoff）与无效证据分开报告。它复用 Tau-Bench 零售与航空领域的真实状态变更工作流，但把测量构造从“任务完成”改成“在指定事务故障下的恢复”。

论文明确列出四项测量贡献：(1) 一个 52 场景的确定性事务故障注入基准，覆盖零售与航空工具 agent；(2) 一套 trace schema 与评估器，对状态增量与场景契约打分而非使用 LLM 评判；(3) 一套有效性记账协议，把晋升终态行、底层尝试与重试、表有效性、交互结果、完整性标签与质量警告分开；(4) 标定与报告控制：带指定标签的合成契约汇总夹具、20 场景 overlay/无-overlay 配对消融，以及保留在行为计数之后的可选次级诊断。其系统动机来自经典可靠性工程：经典 ACID 属性定义了数据库恢复契约（Haerder & Reuter 1983），幂等 API 设计防止歧义失败后的重复副作用（Featonby 2020），saga 模式为长流程补偿提供模型（Garcia-Molina & Salem 1987）；ACID-Bench 把这些思想适配到通过外部工具行动的对话 agent。

## 核心方法
基准构建 52 个确定性故障注入场景，按“场景契约（scenario contract）”组织——每个契约绑定一个 Tau 任务、一个故障计划、一个期望状态转移、失效规则与证据/验证要求。契约是最小数据单元（而非自然语言 prompt），这保证故障点与用户目标因果相关。ACID-Core 40 个覆盖四类各十个：部分提交（multi-write 中后续步骤硬失败，留下需补偿的真实义务）、幽灵成功（ghost-success，写入已提交却返回错误，需检查状态再重试避免重复效果）、过期读（读与依赖写之间状态被改，需刷新后再行动）、崩溃恢复（写提交后 agent 丢失上下文，需从持久状态续跑并验证终态）。Consequence 12 个覆盖证据、验证、预算、危害等后果（写前需有证据、写后需验证、恢复预算受限、需避免用户危害）。场景仅在“用户目标需要可观测状态变更”时准入，纯信息查询任务被排除；且故障必须对测量声明是必要的一一若任务可不经过注入点完成，场景就过弱需收窄契约，避免无关陷阱 prompt。代表性可检视契约包括 A-02（部分提交取消恢复）、I-01（幽灵成功重复防护）、S-02（过期价格刷新）、D-01（崩溃重启验证）与 C-04（后果证据与写后检查）；这些例子被刻意做成操作性而非分类学——若配置故障与用户目标无因果绑定，场景应被修复或排除，从而让测试集贴近可被审稿审计的事务失败而非任意陷阱提示。

每个场景通过静态审计（声明完整：id、domain、Tau task id、fault plan、success tools、evaluator checks、prompt overlay）与追踪审计（配置故障确实触发、痕迹元数据匹配声明、状态增量满足或违反契约）双重校验；若配置的故障没被触发，该行被标为“无效故障暴露（invalid fault exposure）”而非确认模型失败。追踪用统一 schema 记录工具名、参数、真实结果、agent 可见结果、注入故障、前后状态快照、提示条件与来源哈希；评估器据此计算三类常被混为一谈的量：ACID 局部成功（场景断言是否通过）、事务完整性（状态是否被破坏/未恢复）、表有效性（记录是否满足评估器元数据检查），并以 manifest 审查机制隔离不同 prompt 条件（如澄清 overlay 与基础 prompt），防止非匹配样本混入同一张表。脚本化用户协议另加交互轴：故障暴露、安全交接、无效/未暴露、最终记录运行时失败。实现的 Strict Clean Pass（SCP）是表有效 ∧ ACID 局部成功 ∧ 无完整性违例三者交集，不要求原始 fault_exposed 交互结果，故是“会计交集”而非“严格自主恢复率”。评估刻意不引入 LLM 评判，保持结果可复现、可审计。论文把“被测系统”视为复合体：模型行为、提示策略与工具环境需联合测量，而不是拆开独立打分。评估器还输出非失效性质量警告（quality warnings），如偏离标准工具链、缺失写后检查、缺失写前读取、超出恢复预算等；这些警告仍可见，因它们影响解读（尤其 Consequence 轨道），但除非契约把该行为标记为必需，否则不自动判行失效——这避免了把弱证据藏进干净分数、或把每个程序偏离都等同状态损坏。可选次级诊断 Descriptive Triage Index（DTI）把非损坏行为模式（含 SCP、安全交接、故障暴露进展）分解出来，但因权重是待定策略选择而放在主表之外。标定控制用合成契约汇总夹具（synthetic contract-summary fixtures），其标签不在 agent 上执行生成，仅检验聚合与报告是否保留 ACID 局部成功、完整性与指定行为类别的分离；例如 task-only 夹具给 52/52 ACID 局部成功与 52/52 完整性标签，聚合器返回 0/52 SCP，证明管道能保持二者分离，但不证明策略实际表现。最小清单字段（scenario inventory、prompt condition、model config、trace/result paths、Tau 与 ACID 标识符、promotion status）构成 manifest，防止不兼容运行被混入同一分数。

## Performance 概括
在 5 个模型条件档（4 个模型 ID、2 条推理路由）下共得到 780 条晋升的终态记录、对应 800 次底层尝试；其中 525 条带有完整性违规标签。20 次失败尝试影响 14 行，全部 14 行重试后产出完成终态；无晋升终态记录带 runtime_failure（不代表零运行失败）。整体 Strict Clean Pass（SCP）为 234/780（含 18 条安全交接）；5 个档 SCP 区间 36/156–57/156（0.231–0.365）。配对 prompt 消融显示：澄清 overlay 下 27/60 达到 SCP，基础 prompt 下仅 2/60（27 条 overlay-only、2 条 base-only、0 条两者皆达、31 条皆未达）。525 个完整性标签中 335 个落在故障暴露结果上、98 个在安全交接上、92 个在无效/未暴露上，说明并非所有完整性标签都是暴露故障后的失败证据。ACID 局部标签与 Tau 奖励在 285 条上分歧（44 条 ACID 成功但 Tau 失败、241 条相反），证明二者是不同维度。

## 论文价值与不足
价值在于把“任务成功”与“状态完整性、故障暴露、安全交接”分离评估，并以 manifest 审查、有效性记账（validity accounting）和确定性评估把“被测系统”作为复合体联合测量，刻意保守地声明这只是测量方法贡献而非模型排名。其 SCP 作为“会计交集”的诚实定义避免了把安全交接误算成自主恢复，这是其方法学纪律性的体现：低 SCP 可能源于表无效、ACID 断言失败或完整性标签任一原因，而非简单等同于“模型不可靠”。不足是底层行与原始 trace 未公开（仅本地 manifest 审查证据），领域仅限零售与航空，缺少支付、医疗、工业控制等关键域；作者也明确说明该基准不构成部署安全认证或决定性的模型比较结论，3 次重复的档不估计模型间/提供商间方差。在 artifact 层面，实现与 52 个已校验场景契约在本地准备、拟以 MIT 许可发布，但当前没有经验证公开仓库或 camera-ready 附件，底层行与原始 trace 也未公开，故可复现性依赖未来档案化证据发布或按命名条件重新运行。作者给出可证伪条件：若审稿审计发现许多注入点与用户目标无因果必需、触发匹配反复阻断语义有效路径、无 overlay 与澄清 prompt 在更大复制下产生相同失败模式、或合成夹具标签未能按指定聚合，则主张会削弱——这些失败模式本身是测量证据而非模型质量证据。构造有效性方面，本地校验含一个 18 行 trace 审计样本，使用七种紧凑无效暴露边角标签，其中精确前置或触发匹配严于语义任务路径。

## 工业界落地可行性评估
可行且有明确落地价值。其“确定性故障注入 + 状态化审计”范式非常适合作为有状态工具 agent 上线前的回归测试和持续评估基线，尤其适用于电商、出行等涉及订单与状态变更的系统；论文更建议把它作为部署后生命周期监控的前置行为基线，而非替代监控——在监控漂移、回归或 API 诱发行为变化前，先要有确定性方式测 agent 在已知事务故障下是否保全外部状态。但要支撑生产环境采信，仍需扩展领域覆盖、补充支付/医疗等关键场景、增加推理路由与模型覆盖、重复 prompt 消融与不确定性分析，并公开评测产物以便复现与审计。其 SCP 与完整性标签也应作为诊断画像而非单一排序分数来读，因为同一条件低 SCP 可能源于表无效、ACID 断言失败或完整性标签中任一原因。落地时还需注意其运行协议的操作纪律：每个模型条件使用隔离的 trace 与结果目录，同一测量窗口只对应一个命名条件（run isolation），否则评估器无法区分缺失行与陈旧行、也无法干净报告每模型成本增量；这与纯打分无关，却与可复现性同等重要。ACID-Bench 因此更适合作为部署前确定性基线与部署后持续评估之间的接口层：它定义的审计失败模式与 trace 级指标可复用进连续评估流水线，而监控本身负责检测漂移、回归与 API 诱发的行为变化——前者提供“已知事务故障下外部状态是否保全”的确定性答案，后者在生产中持续观察。
