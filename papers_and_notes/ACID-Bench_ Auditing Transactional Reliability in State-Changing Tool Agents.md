# ACID-Bench: Auditing Transactional Reliability in State-Changing Tool Agents

## 背景与 Idea
会修改持久状态的工具型 agent（如取消订单、改地址、订票）即便对话看起来"成功"，也可能留下重复写入、过期读（stale read）、部分提交（partial commit）等状态损坏。ACID-Bench 把这类"事务可靠性"单独作为评估对象，主张用确定性的故障注入加基于状态的评估（不依赖 LLM judge）来量化 agent 在受控事务故障下的恢复能力，从而把"任务是否成功"与"状态是否完好"分开度量。

## 核心方法
基准构建 52 个确定性故障注入场景：ACID-Core 40 个覆盖部分提交、幽灵成功、过期读、崩溃恢复等；Consequence 12 个覆盖证据、验证、预算、危害等后果。每个场景用 trace schema 与确定性状态评估器打分，分别统计 ACID 局部成功、事务完整性、表有效性、交互结果和完整性标签，并以 manifest 审查机制隔离不同 prompt 条件，防止非匹配样本混入。评估刻意不引入 LLM 评判，保持结果可复现、可审计。

## Performance 概括
在 5 个模型条件档（4 个模型 ID、2 条推理路由）下共得到 780 条晋升的终态记录、对应 800 次底层尝试；其中 525 条带有完整性违规标签。整体 Strict Clean Pass（SCP）为 234/780（含 18 条安全交接）。配对 prompt 消融显示：澄清 overlay 下 27/60 达到 SCP，基础 prompt 下仅 2/60（27 条 overlay-only、2 条 base-only、0 条两者皆达、31 条皆未达）。

## 论文价值与不足
价值在于把"任务成功"与"状态完整性、故障暴露、安全交接"分离评估，并刻意保守地声明这只是测量方法贡献而非模型排名。不足是底层行与原始 trace 未公开，领域仅限零售与航空，缺少支付、医疗等关键域；作者也明确说明该基准不构成部署安全认证或决定性的模型比较结论。

## 工业界落地可行性评估
可行且有明确落地价值。其"确定性故障注入 + 状态化审计"范式非常适合作为有状态工具 agent 上线前的回归测试和持续评估基线，尤其适用于电商、出行等涉及订单与状态变更的系统。但要支撑生产环境采信，仍需扩展领域覆盖、补充支付/医疗等关键场景，并公开评测产物以便复现与审计。
