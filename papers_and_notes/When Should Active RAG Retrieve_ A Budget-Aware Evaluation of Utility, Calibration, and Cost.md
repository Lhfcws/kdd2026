# When Should Active RAG Retrieve? A Budget-Aware Evaluation of Utility, Calibration, and Cost

## 背景与 Idea
检索增强生成（RAG，Retrieval-Augmented Generation）指在生成答案时从外部语料检索证据片段拼接进提示，以补足模型参数记忆的不足；它在知识密集型任务上能显著提升准确性，但代价是更长的提示、额外的检索与推理开销，以及可能引入无关或噪声信息。近年的高效检索与端侧检索研究进一步把这种"质量—成本"权衡在系统层面显性化，要求同时考虑检索质量、能耗与资源占用。传统 RAG 要么全程不检索、要么全程检索，而 active RAG（主动检索，也称 agentic RAG、self-adaptive retrieval）让 agent 在生成过程中自主决定"何时"检索外部知识——例如仅在低置信度 token 出现时触发（FLARE）、或训练模型自省是否检索（Self-RAG）、或按查询复杂度在"不检索/单步/多步检索"之间切换（Adaptive-RAG）、或在生成时实时估计信息需求（DRAGIN、UAR）。这类系统的核心难题是"何时该检索"，但作者指出这个短语其实掩盖了一个运行点（operating-point）问题：两个都自称"检索预算 50%"的 active RAG 系统，在独立测试集上实际触发检索的比例可能完全不同，于是更高的准确率可能只是因为它偷偷用了更松的预算，而非检索策略更优。

作者因此把 active RAG 重新框定为预算效用估计（budgeted utility estimation）问题：在给定检索预算下同时权衡效用、校准与成本，而不是沿用"相似度或置信度低于某阈值就检索"这类单一触发启发式。这一视角暴露出无预算对比会掩盖的四类失败模式。第一，效用异质性（utility heterogeneity）：检索对某题可能有帮助、无影响、也可能有害，并非"检索总比不检索好"。第二，排序失败（ranking failure）：触发分数未必能把"该检索"的样本排在"不该检索"之前。第三，校准失败（calibration failure）：在标定集上满足预算的阈值，在部署数据上可能突破预算。第四，成本记账失败（cost accounting failure）：证据使用率并不等于真实部署成本，因为不确定性路由器、探针式检索路由器、学习型路由器在生成、检索、提示 token 三方面的开销各不相同。本文的贡献是把这些运行点变得可比较，而非评出一个"万能路由器"；其目标不是加冕某个通用路由器，而是展示未来的 active RAG 系统应如何在显式、可复现的运行点上被比较。

从工程视角看，这一问题在生产企业检索系统时尤为尖锐：检索预算直接转化为推理延迟与按调用次数计费的开销，若两个团队各自宣称"用了 50% 检索"却实际触发率分别为 30% 与 70%，它们的准确率差异完全可能来自预算松紧而非算法优劣。论文因此主张，任何 active RAG 的对比都必须同时报告真实使用率、阈值转移误差、危害率与成本分解，否则结论不可比。这一立场也呼应了相邻工作：基于推理时自主度的 agentic Text-to-SQL 分类学、把检索选择视为鲁棒性—精度权衡的文档路由式 RAG，都把"何时检索"当作一个受约束的决策，而非单纯的准确率问题。对部署方而言，最务实的启示是先把"名义阈值"替换为"保守分位数阈值"，以有限样本松弛换取部署时不突破预算。

## 核心方法
效用被定义为"使用检索证据相对不检索答案的边际正确性变化"：对每个问题 q_i，记 no-retrieval 答案 a_i0 与检索上下文答案 a_iR，净效用 u_i = correct(a_iR, y_i) − correct(a_i0, y_i)，并量化为三元标签 u_i ∈ {−1, 0, +1}，分别对应有害、中性、有益检索；这正是笔记中 benefit（有益比例）与 harm（有害比例）的来源。论文进一步区分了三个常被混为一谈的评估对象，即三条 frontier（前沿）。精确前沿（exact frontier）按路由器分数对独立测试样本排序，在预算 ρ 下检索排名前 ⌊ρn⌋ 个样本，它不可部署，但能在"使用量对齐"的条件下诊断排序质量。可部署前沿（deployable frontier）在标定集上选阈值、原样套用到独立测试集，测量阈值的跨集转移与真实使用率。保守前沿（conservative frontier）则用带有限样本松弛的更严阈值，以牺牲部分准确率为代价降低部署时的预算违规。这三条前沿的区分正是为了回答部署者部署前必须回答的四个问题：检索效用是否真的异质、分数能否排好序、标定的阈值能否守住未来预算、结论在模型与证据变化时是否仍成立。

触发器的评估覆盖四个家族共七个触发分数。查询复杂度类用一个模仿 Adaptive-RAG 的基线，仅看问题文本与廉价的查询复杂度特征。不确定性类包括"生成 no-retrieval 答案时各 token 的平均熵"与"最小 token 置信度"（1 减去生成中最大 token 概率的最小值）。检索分数类包括 BM25 最高分与 BM25 边际（前两名 BM25 分数之差）。学习型类则是预算效用路由器 BUR（Budgeted Utility Router），它的线性版本在 u_i ∈ {−1,0,+1} 上训练多项逻辑回归，输出 P(u=+1)−P(u=−1) 作为期望净效用评分，另有梯度提升变体 BUR-GBM，特征融合生成不确定性、BM25 分数、答案长度与问题长度。作者强调"分数"与"运行点"的区别：分数只要能把高效用决策排到前面就有用，但部署还需要一个在未来输入上守预算的阈值。

校准方面，名义阈值（nominal threshold）按目标使用率 ρ 标定，但作者指出名义 50% 目标本身不等于观测到的预算，因此在标定集上会突破目标。论文据此评估一个保守分位数规则：阈值选在 ρ_safe = max(0, ρ − ε)，其中 ε = √(log(2/δ)/(2·n_cal))，源自 DKW 风格的有限样本松弛，经验上应降低独立集的预算违规，代价可能是准确率稍降。成本模型则把预算定义为"最终答案使用检索证据的样本数"，并对不同触发家族分别记账，因为各家族在决策前付出的成本不同：查询类路由器在决策前只付廉价查询特征费；不确定性路由器把 no-retrieval 生成本身当作决策前计算，被跳过样本直接复用该答案，触发样本才付检索与第二次生成；检索分数类在决策前先付一次探针检索（其成本可被触发样本复用）；全特征 BUR 则在决策前同时做 no-retrieval 生成与探针检索。这种分解虽窄于完整部署延迟模型，但能显式暴露运行点，避免把触发计算与检索上下文作答混为一谈。

实验设置上，主实验在三个知识密集型多跳 QA 数据集（HotpotQA distractor、2WikiMultiHopQA、MuSiQue，其中 MuSiQue 过滤为可回答样本）上进行，使用 Qwen2.5-1.5B-Instruct，每数据集 2000 个验证样例、固定随机种子，检索为该问题候选段落上的 BM25 top-5，答案以标准化后精确匹配或 token F1 > 0.80 计分。为做非 Qwen 家族的稳健性检查，另用 SmolLM2-1.7B-Instruct 跑 HotpotQA、Granite-3.1-2B-Instruct 跑 HotpotQA 与 2Wiki。每个数据集按效用类别分层切分为标定集与独立测试集，阈值只在标定集上选，主表用 CPU 上的五折评估，预算集合为 {10, 25, 50, 75, 90}%，报告均值准确率、使用率误差、违规率、精确前沿与保守前沿。为测试结论在噪声证据下是否成立，还做了 HotpotQA 全局候选 BM25 与稠密检索（E5-small）诊断，把每题独立候选池换成覆盖全部去重候选段落的共享池，以加入跨例检索噪声。

## Performance 概括
HotpotQA 上 no-RAG 准确率 15.4%，always-RAG 43.4%，检索 benefit 31.9%，harm 4.0%。nominal 50% 阈值在 28.6%–65.7% 的不同 split 上出现校准违规，说明固定阈值触发检索并不稳健，需预算感知的效用估计。补充细节：2Wiki 上 no-RAG 21.3% → always-RAG 28.5%，但 harm 高达 8.8%，故检索收益更有限；MuSiQue 最难，no-RAG 2.2% → always-RAG 11.9%。在更噪的全局 BM25 下，always-RAG 由 43.6% 降到 34.6%、harm 由 3.4% 升到 5.8%，最佳路由器 exact-50 由 34.8% 降到 30.0%；换用稠密 E5-small 检索部分挽回（38.6%、harm 3.8%），但仍低于每题候选设定。排序上各触发器接近：HotpotQA 50% 目标下 BUR-linear 可部署 33.8%、最小置信度 33.3%、熵 32.9%、Adaptive-RAG 基线 31.8%，而 oracle 为 45.9%，差距本身说明应同时报告真实使用率与精确诊断而非只看目标预算；分折违规率在"只要超一点就算"口径下达 40%–100%，故还需报告容忍度口径的超用率。

## 论文价值与不足
价值在于把 active RAG 的触发决策从"阈值启发式"提升为可度量的预算效用估计，明确给出四类失败模式与三条 frontier，量化了 benefit/harm 与校准缺口，并揭示"简单的不确定性或检索分数基线常能与学习型效用路由器媲美"。其评价框架可直接指导检索触发策略的选型与阈值设定，并为多跳 QA 以外的任务提供"效用—成本"权衡视角。具体而言，它纠正了一个常见误区：部署者往往以为"我把阈值设成 50% 就控制了检索预算"，而论文证明名义目标并不等于观测到的预算，必须报告真实使用率、阈值转移误差、危害率与成本分解，而不能只报准确率。

不足主要有三：一是实验以单一小模型 Qwen2.5-1.5B 为主线，虽补了 SmolLM2、Granite 两个非 Qwen 家族检查，但大模型与代码生成、agent 工具调用等场景的泛化未验证；二是效用 u_i 的三元定义依赖每数据集的 gold 标注，跨域迁移需重新标定，且 no-RAG 与 always-RAG 两次生成带来的成本本身未被计入对比；三是 BUR 作为参考学习型路由器，其内部特征与训练依赖具体数据，结论更偏"评价协议"而非"推一个通用路由器"。此外，成本模型刻意窄于完整部署延迟模型，未计入检索系统本身的延迟与货币成本，也未按提示 token 与生成 token 的不同单价细分。

## 工业界落地可行性评估
RAG 是企业知识问答、文档助手与 agent 工具检索的核心组件，而"在固定证据/算力预算下该给哪些输入检索"正是生产系统天天面对的取舍：检索多了延迟与 API 成本上涨、检索少了答案可能出错。本文的预算感知评估框架（分效用异质性、排序、阈值转移、成本记账四条线）可直接用于上线前的触发器选型：用精确前沿看候选路由器排序质量、用可部署前沿测阈值在真实流量上的使用率、用保守前沿为成本敏感场景兜底。对落地最实用的一点是——不确定性/检索分数等轻量基线往往不输学习型路由器，意味着很多场景无需训练额外模型即可获得可用的主动检索策略，降低了工程与维护成本。

落地时可先把"名义阈值"替换为"保守分位数阈值"，以有限样本松弛换取部署时不突破预算；再根据业务对延迟/成本的敏感度在 {10,25,50,75,90}% 的预算网格上选运行点，并把真实使用率作为上线监控指标而非只看准确率。局限在于，企业真实检索多面对网页级或私有知识库的全量索引，而非论文中每题候选段落的受控设定，证据噪声与检索器家族会同时改变效用与排序，落地时需用自己的语料与流量重新标定阈值；另外本框架评估的是"是否检索"这一决策，尚未覆盖"检索什么、检索几段、如何重排"等更细的检索策略维度。总体而言，这是一套低风险、可直接嵌入现有 RAG 评估管线的工程方法论，落地可行性高，且投入产出比好。
