# A Framework for Evaluating Agentic Skills at Scale

## 背景与 Idea
agent skills（智能体技能）是结构化、可复用的知识工件（artifact），用于增强 LLM agent 的能力：它们把领域工作流、API 使用模式、编码约定、带倾向性的流程选择（opinionated workflow choices）与最佳实践，以结构化形式固化下来。随着各 agent 平台与技能注册表普及，用户可以把通用 agent 专门化到科研、生产力、数据工程、网页开发、基础设施自动化等域。然而一个核心问题长期未被回答：如何严格评测一个 skill 是否真的改善了 agent 行为？现有 agent 榜单多衡量通用解题、工具使用或编码能力，要么不聚焦"skill 如何跨模型改变行为"，要么只依赖少量手工固定任务集，覆盖有限且无法对任意新写 skill 度量其效用。论文（Tessl 团队，伦敦；KDD 2026）因此提出一套规模化评测框架，把"技能"作为评测单元，既能对单个 skill 隔离评估（定位弱点），也能在 500 个真实技能、约 1000 个任务、19 个 agent-model 配置上做横向对比，覆盖真实的技能与任务分布。其价值定位是：给 skill 作者一把具体工具，回答"给定一个新 skill，它是否在预期任务上提升了表现"——这一问题又可分解为：agent 是否遵循 skill 编码的指令？skill 是否提供了模型原本不具备的信息/工作流/偏好？skill 是否改善了任务完成、还是只改变了表层行为？以及接入 skill 能否让更小/更便宜的模型匹配更大模型的性能？

这个问题的现实背景是 skill 生态的爆发：各社区注册表（如论文所用的 tessl.io/registry 及 Anthropic、Google 等官方技能源）已聚集大量由不同组织贡献的技能，覆盖从"迁移 huggingface-cli 到 hf 命令"这类具体工程技能，到科研、金融、文档等广域主题。但同时，固定基准套件只给每个技能配一套写死的任务，无法回答"我刚写了一个新技能、它到底有没有用"——而这正是技能作者日常面对的问题。本文的方法论贡献，正是把"评测任意新技能"变成可规模化、可自动化的流水线，而不是依赖少数手工策划的标杆集。这也解释了为何论文特意设计"单个技能隔离评估"这种此前技能基准不具备的能力：它让作者能定位某个技能的薄弱环节（是没改善目标完成、还是没改变指令遵循），从而指导技能迭代，而非只给一个总体分数。

## 核心方法
框架把一个或多个 skill（可选地由用户意图引导）转成可执行评测任务：每个任务是一条真实用户请求，配齐所需环境、输入工件与隐藏评分量规（rubric，即评分量规，用自然语言写明的断言清单）。流水线由三类专门 agent 协作构建并自检。环境工程 agent（environment engineering）先判断技能所需资源能否在求解时构造，论文把环境依赖归为 15 类：Tool/CLI 访问、MCP 服务、外网/API、认证凭证、环境变量、运行时/语言、多轮评估、现有仓库、外部代码文件、git 状态、数据库、浏览器/UI、本地服务、输入基线文件、预置外部状态；在全自治模式下会丢弃需要现有仓库、预置外部状态、本地服务等难以满足的技能。任务生成 agent（task generation）基于 skill 内容或用户反馈生成任务提案，并指定输入需求（如 PDF 处理技能需不同 PDF），把提案转成含任务描述、输入文件夹、可验证环境与评分量规的可执行任务规范，每个 skill 最多生成 3 个多样任务。验证/质检 agent（validation）筛除歧义任务与不一致环境，确保任务描述不泄露求解步骤、不暴露量规细节以防作弊；失败质检的任务被丢弃，因此每 skill 最终可能少于 3 个。流水线可端到端自治运行，也支持 human-in-the-loop：人工可在每阶段检视、修改、批准中间产物，实践表明混合模式产出质量最高，因为人工能纠正模糊需求、补全输入、捕捉细微验证失败并控制难度。

评分用两套量规，每套由若干 1–10 分的自然语言断言组成、合计 100 分，由 LLM-as-judge 打分：指令遵循量规（instruction-following）评估解是否遵循 skill 编码的偏好——库选择、结构约定、命名规则、禁用模式、必要步骤；目标完成量规（goal-completion）评估是否产出所请求的正确产出物。两者 delta 的差异有诊断意义：goal-completion 大幅领先说明 skill 提供了基础模型不具备的知识/能力；instruction-following 大幅领先说明 skill 改变了 agent 的"行为方式"。最终分数为两者加权，权重依用例而定。论文还特意用"有/无 skill"两种条件各解一次同一任务，用差值（skill delta）估计 skill 的边际效用；实验中显式告知 agent skill 已安装可用，以隔离"skill 一旦被调用时的效用"与"agent 能否识别其相关性"这两个不同问题——真实部署中用户未必指明用哪个 skill，但本设定让作者能专注度量技能本身价值。

数据构建上，作者从公共聚合平台（tessl.io/registry）采集约 500 个真实技能，聚焦 Anthropic、Google、ElevenLabs、Shopify 等约 100 家知名组织的热门技能，下载完整 SKILL.md 与支撑文件；过滤掉非宽松许可（保留 MIT、Apache 2.0）、格式错误与按内容去重的技能，并用 Snyk 安全扫描剔除恶意技能。环境需求分布显示：Tool/CLI 访问 70.4%、认证凭证 66.0%、运行时/语言环境 65.2%、外网 42.0%，而现有仓库 19.3%、MCP 16.2%、多轮评估 7.0%、其余各类均 ≤4.4%，说明绝大多数技能依赖命令行/凭证/运行时，少数依赖复杂环境。任务生成在全自治模式进行，最终得约 1000 个任务，覆盖编程/软件工程（Web/UI、ML/AI、DevOps、测试、API）与科研、金融营销、文档、生产力等主题；聚类显示技能主要围绕软件工程，其余分布在科研、金融营销、内容文档、个人生产力。

实验设置上，评测 19 个 agent-model 配置（开源与专有并存），用 Claude Code、Codex CLI、OpenHands 等 harness，统一以 Sonnet 4.6 作 judge agent，每个任务在有无 skill 两条件下各解一次，共约 38,000 条有效轨迹（轨迹有效指 agent 通过/失败/超时但未发生基础设施或运行时错误）。模型含 Anthropic 全系（Haiku 4.5 到 Opus 4.8）、OpenAI GPT-5.4 系列、Google Gemini 系列，以及 GLM 5.1、DeepSeek V4、Kimi K2.6、MiniMax 2.7、Qwen3-Coder-Next、Nemotron 3 等开源模型，经 Fireworks AI 或 Amazon Bedrock 服务。指标除两套分数外，还报 skill delta、运行时、成本与 token 消耗。论文还探索了框架的三种用法方向：(1) 单 agent 在受控条件下有/无 skill 各解，估计技能边际价值并识别其改变行为是有用、冗余还是无效；(2) 多 agent 解同一任务，为给定任务选合适模型；(3) 固定 agent 生成多任务，暴露 skill 的弱点——第三种能力据称是此前技能基准都不具备的。

## Performance 概括
在公开结果图（图 1）中，Opus 4.8 以 88.0 最高，Opus 4.7 为 87.7；GLM 5.1 达到 85.0，表现接近头部。Kimi K2.6、MiniMax 2.7、Qwen3-Coder-Next、Gemini 3.1 Flash Lite 等约在 57–60 区间；Nemotron 更低。更细的"有 skill"加权总分组里，GLM 5.1 凭开源权重达 91.1，几乎追平 Sonnet 4.6（91.5）与 Opus 4.8（92.7）、Opus 4.7（92.3），仅差 1.2–1.6 分；而 GPT-5.4 mini（84.5）与完整 GPT-5.4（88.2）、DeepSeek V4 Flash（83.9）与 V4 Pro（86.6）差距均被 skill 收窄到数分，说明 skill 把家族内小模型推到接近旗舰。成本上 GLM 5.1 每场景约 $0.89，对比 Sonnet 4.6 的 $1.46、Opus 4.8 的 $3.26、Opus 4.7 的 $3.94，以三到四倍更低成本拿到近前沿质量。skill delta 相对增益 5.5–22 分，主要由 instruction-following 驱动；Nemotron 几乎无受益，Kimi K2.6 仅 +7.1，说明并非所有模型都能善用 skill。结果刻画了不同模型配置在规模化技能评测下的明显梯队。

## 论文价值与不足
价值在于提供大规模、可复现的技能评测方法论与可比排行榜，对 agent 选型与成本优化有直接参考意义：它证明"配对一个 skill 与更便宜的模型"可逼近昂贵旗舰模型，且首次支持对单个 skill 隔离评估以定位弱点，并开源了评测数据集（HuggingFace: tesslio/task-evals-for-skills）。按技能域的 uplift 还给出实用启发：能把知识编码成"工作流"的域（Media & File Processing +38.1、Productivity & Communication +32.5、Security & Compliance +30.3）增益最大，而只声明指南/最佳实践的域（Testing/QA +16.7、Scientific +17.0）增益最小——即"可被流程化的知识最适合做成 skill"，因为清晰步骤易遵循却难凭空发明。不足在于：其一，任务由框架自动生成，goal-completion 对前沿模型常饱和（>90%），说明合成任务难以区分最强模型能力，可能与真实生产分布存在偏差；其二，human-in-the-loop 虽提升质量，但带来较高成本，难以无限扩展；其三，全自治模式下为可执行为由丢弃了需复杂环境的技能，使技能覆盖有偏；其四，LLM-as-judge 本身有评判偏差，且是否真能反映生产环境行为仍待外部反馈验证；其五，真实部署中"agent 能否识别 skill 相关性"这一环节未被本实验覆盖（实验显式告知 skill 可用），因此技能实际效用可能低于 measured delta。

## 工业界落地可行性评估
落地性强：企业可用该框架对内部 agent skills 做常态化、规模化的评测与回归，支撑模型/agent 选型与成本决策，框架化、可复现的特性使其易集成进 CI/CD 式评测流水线。最直接的落地动作是：用"有/无 skill"差值挑出高价值技能域，把昂贵前沿模型替换为"skill + 便宜模型"组合以降本；并在 skill 上线前用指令遵循量规检查其行为是否符合团队约定。落地障碍主要有三：一是自治生成任务对前沿模型区分度不足，关键任务仍需 human-in-the-loop 补充难度与真实性；二是 LLM-as-judge 需搭配人工抽检以防评判偏差累积；三是环境依赖（凭证、私有仓库、数据库）在内部落地时需补齐真实资源，否则任务不可执行、评测覆盖受限。此外，企业需注意"显式告知 skill 可用"的实验设定与真实"agent 自主识别 skill"之间存在落差，上线前宜补一轮无提示的端到端验证。

需要强调的是，skill delta 的提升在构造上偏向"有 skill"条件（因为 delta 正是有/无 skill 之差），所以论文也坦言这一结果部分由设计预期；真正有信息量的是"不同模型从同一 skill 获益程度差异极大"——Nemotron 几乎不受益、Kimi K2.6 仅 +7.1，而前沿与 GLM 系列获益 16–22 分，说明模型"是否会用 skill"与"能力上限"是两件事。对落地最实用的推论是：若目标技能域属"可流程化"类（Media/Security/Productivity 等 uplift 居前），则应优先投入 skill 工程，并用"便宜模型 + skill"替代昂贵旗舰以降本；若技能域偏"声明式指南"（Testing/QA、Scientific 等 uplift 垫底），则 skill 收益有限，应更关注模型本身能力或把指南转写成可执行步骤。论文还给出每模型的运行时、成本与 token 消耗明细，企业可直接用这些 curve 在"质量—成本"平面上做选型，而非仅看排行榜总分。

从工程落地节奏看，框架最适合两类团队：一是维护内部技能库的平台方，可用它对每个新技能跑"有/无"对比，自动标记 delta 偏低的弱技能并反馈给作者迭代；二是做模型选型的架构组，可用 19 配置的横评快速决定"哪些任务交给便宜模型 + skill、哪些必须上旗舰"。论文同时提醒，goal-completion 在多数模型上已饱和（>90%），说明当前合成任务区分不开最强模型——这意味着若你的真实任务同样偏"能否完成"，则应更看重 instruction-following 维度与成本，而非被总体分误导去追更高档模型。最后，数据集已在 HuggingFace 开源（tesslio/task-evals-for-skills），团队可在此基础上补自有领域任务，把"通用技能排行榜"升级为"我司技能回归测试"，使评测随技能库演进持续有效。
