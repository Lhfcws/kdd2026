# The Scaffold Effect in Coding Agents: Harness Choice as a Hidden Variable in Coding-Agent Evaluation

## 背景与 Idea
公开编程智能体排行榜（coding-agent leaderboard）通常以模型名与通过率（pass rate）排名，但模型外围的 harness / scaffold（中文常译作"脚手架"或"运行框架"）常被含糊处理——它是一层负责下发工具、管理上下文、决定何时停止的软件，包裹在模型之外。作者指出：只有当 harness 固定时，模型之间的比较才有效；一旦 harness 变化，性能与效率就混淆了"模型效应"与"脚手架效应"，让人分不清分数差异到底来自模型还是来自框架。这个问题并非凭空而来：Terminal-Bench 2.0 论文曾报告 Claude Opus 4.5 在两种不同 harness 下分别取得 52.1% 与 57.8% 的通过率，却消耗 256.9M 对 3.9M 输入 token——为 5.7 个百分点的准确率提升付出了约 65 倍的 token 代价。本文把这种观察系统化为受控研究，提出所谓"脚手架效应"（scaffold effect）：主张 harness 选择是编码 agent 评估中被忽视的隐藏变量，必须作为受控因子。其视角是"人本位"（human-centered）的——真正使用 agent 的开发者关心的是每任务成本、完成时延与需要多少人工监督，而不是仅看模型名的分数。因此论文的核心主张是：以人本位视角做编码 agent 评估时，比较的单位应当是 harness–model pair（脚手架与模型的配对），而非单独的模型名；排行榜除通过率外，还应报告 token 用量、时延与失败类别等部署相关信号。更根本地说，“harness 是隐藏变量”这一论断挑战了排行榜的方法论预设：排行榜默认把分数差异归因于模型，但脚手架决定了上下文怎么拼、工具怎么暴露、何时停、失败后怎么重试，这些都会系统性改变 agent 表现，却不在“模型名”里。作者引用 Wang 等人“agents are systems rather than models”的观点，强调评测对象应是整个系统；他们也指出 SWE-bench 等基准虽注意到 scaffold 影响分数，却把它当“要控制的混杂项”而非“要研究的现象”，本文则反其道而行，把 harness 本身变成自变量。人本位视角进一步把“开发者真正在乎什么”摆上台面：一个每天用 agent 的人不会为“模型名 +x 点通过率”买单，而会为“每解决一个任务花多少 token、等多久、要不要我盯着它别卡死”买单——后三者才是 dollar cost、latency、supervisory effort 的来源。Terminal-Bench 2.0 那个 65× token 换 5.7pp 的例子，正是这种错配的极端写照。从方法论上说，本文把 harness 从“被控制的混杂项”提升为“自变量”，等于承认评测结论只在“同 harness”条件下才可比较；一旦换了脚手架，排行榜的数字就失去了跨系统可比性。这也是为什么很多团队在自家环境复现榜单分数时严重打折——他们用的 harness 与榜单提交者不同，而这一点在榜单表格里从不标出。

## 核心方法
实验在 Terminal-Bench Pro（400 个跨 8 个领域、每任务约 28 个 pytest 测试的任务集）上，用分层抽样取 50 个任务，覆盖 8 类原型：BUG（修 bug）、BUILD（编译/环境搭建）、DATA（数据转换/解析）、IMPL（从零实现）、ML（模型训练/评估）、PUZZLE（谜题/游戏）、SEC（安全/取证/恢复）、SYS（系统/服务配置）。被测模型为两个近期强编码模型 Qwen 3.6 Plus 与 MiniMax M2.5，跨 3 个开源 harness 共做 300 trials：Goose（源自 Block 公司、现属 Agentic AI Foundation，重度向上下文预注入文件树）、OpenCode（anomalyco 维护，持久工具循环、无自动上下文预加载）、OpenHands-SDK（可组合的软件工程 agent SDK，含微智能体架构、子智能体委派与显式验证）。统一项为：原始任务说明、原生测试套件、Daytona 沙箱、900 秒墙钟上限、OpenRouter 网关、基本相同的 system prompt；不统一项（即研究对象）为各 harness 原生工具 API、自动上下文预加载与内部重试/子智能体逻辑——例如 OpenCode 不暴露 turn-budget 标志，仅受墙钟约束，而 Goose 与 OpenHands-SDK 强制 40-turn 上限。执行基础设施用 Harbor 框架，它用单一任务清单（task manifest）统一驱动这些 harness。指标除 solved 外，还包括 turns（轮次）、tokens_total（按调用方计费口径、不跨供应商归一化，故 Goose 经 Harbor 只报总量无输入/输出拆分）、no-action turns（既未改文件也未发命令的轮次，作为人工监督负担的代理）、wall_seconds，以及 6 类失败分类（REASON/VERIFY/TIME/MAX_TURNS/HANG/ERROR，分类采用 exception-first 决策树，如 AgentTimeoutError 映射到 TIME）。通过率与每解决任务 token 数均报告 95% 配对任务 bootstrap 区间（B=10,000），以任务为配对单元衡量置信度。8 类原型的具体含义值得展开：BUG 是修已有 bug，BUILD 是编译/环境搭建，DATA 是数据转换与解析，IMPL 是从零实现功能，ML 是模型训练或评估，PUZZLE 是谜题/游戏求解，SEC 是安全取证与恢复，SYS 是系统/服务配置——它们覆盖了命令行 agent 的典型工作面，使 50 任务抽样不至于偏在某一类。执行基础设施 Harbor 用单一 task manifest 统一驱动三个 harness，保证“任务相同”这一受控前提；OpenRouter 网关则在各模型原生 API 之上做统一路由。失败分类采用 exception-first 决策树：先看异常类型（如 AgentTimeoutError → TIME），再看是否到达 MAX_TURNS、是否 HANG、是否验证失败（VERIFY）或推理失败（REASON），这让不同 harness 的“死法”可比较。统计上，因 n=50 下每任务就是 2 个百分点，必须通过区间而非点估计判断差异是否显著；也正因此多数通过率差异落入噪声带，而 token 量的 40× 量级差因其锚定在总量上稳健得无需纠结方向拆分。另一容易被忽略的受控细节是统一项与变量项的边界：作者刻意统一了原始任务说明、原生测试套件、Daytona 沙箱、900 秒墙钟、OpenRouter 网关与基本相同的 system prompt，只让各 harness 的原生工具 API、自动上下文预加载和内部重试/子智能体逻辑不同——这种“只动一个因子”的设计才是能干净归因到 scaffold 的前提。Goose 重度预注入文件树、OpenHands-SDK 带子智能体委派与显式验证、OpenCode 持久工具循环且无自动预加载，三者的架构差异本身就解释了为何 token 与 no-action turns 分化如此剧烈。

## Performance 概括
配对通过率差异很小：同一模型内 harness 差异仅 2–8pp，跨模型同 harness 为 4–10pp，n=50 下多数配对差在 bootstrap 噪声内（最大 −8.0pp 的 CI 为 [−18.0, 0.0]）。但每解决任务 token 数（核心效率指标）排序两模型一致：Goose ≪ OpenHands-SDK < OpenCode，OpenCode 比 Goose 高约 40×，且非由 turn 数驱动（OpenCode 平均 21–27 turns，仅 Goose 的 ∼1.2×）；bootstrap 显示 Goose 上限（40–61K）远低于 OpenCode 下限（733K–1.01M），量级差稳健。OpenCode 平均 no-action turns 为 2.0–2.16，是 Goose（0.2–0.3）的约 10×，跨模型复现。失败指纹跨模型一致：Goose 为 REASON 主导（卡住即停、零 VERIFY），OpenHands-SDK 为 VERIFY+MAX_TURNS，OpenCode 为 TIME+idle spinning（零 VERIFY）；Pareto 图上 Goose 居前沿、OpenCode 被两模型双重支配。

## 论文价值与不足
价值在于用受控实验把"harness 是隐藏混淆变量"系统化为证据：成本侧不对称压倒性（harness 改 tokens/solved 达 40×，而模型升级仅 1.0–1.3×），且失败指纹跨模型复现证明其为 scaffold 属性而非模型属性；no-action turns 作为"每任务等待税"（per-task oversight tax）的代理，让人直观看到监督负担的差别，而不只是 token 税。据此提出的"人本位编码 agent 评估单位应为 harness–model pair"，并建议排行榜除通过率外报告 tokens/solved、no-action turns 与失败类别向量，对基准标准化有现实意义。不足：仅 2 模型、3 harness、50 任务，n=50 下每个任务对应 2 个百分点，许多通过率效应在 bootstrap 噪声内仅作描述性；Goose 经 Harbor 仅报 token 总量、无输入/输出拆分；turn-budget 不统一（OpenCode 仅墙钟）且"turn"本身为 harness 定义（每轮内部 LLM 调用数可能不同）；结论不应外推至未评估的闭源商业产品或所有脚手架架构；OpenRouter/供应商默认参数（采样、路由、模型版本）可能随运行漂移，精确复现需固定当时的 provider route 与采样设置，论文已用 released run metadata 记录当时配置。本文的方法论贡献在于把“harness 混淆”从一句直觉变成可复现的量化证据，且其最大张力在于方向不对称：通过率几乎不随 harness 变（2–8pp），成本却随 harness 剧变（40×），意味着“换框架”比“换模型”对账单的影响大一个数量级，而排行榜完全不反映这一点。失败指纹跨模型复现是另一关键证据——Goose 永远 REASON 主导且零 VERIFY（卡住就停、不自我验证），OpenHands-SDK 为 VERIFY+MAX_TURNS（爱验证但撞轮次上限），OpenCode 为 TIME+idle spinning（空转耗时被墙钟杀），这种“指纹”属于 scaffold 而非模型，因此选型时不能只看模型分，还要看它跑在哪个 harness 上的“死法”是否可接受。不足方面除已述样本量、token 拆分、turn-budget 不统一外，还有 Provider defaults 漂移风险：OpenRouter 与上游供应商的采样参数、路由、模型版本可能随运行变化，精确复现必须 pin 住当时的 provider route 与采样设置。对基准设计者的启示是：既然 harness 能单方面制造 40× 成本差而几乎不动通过率，那么任何只报 pass rate 的编码 agent 榜单都在隐式假设“读者不在乎账单”，这与真实部署脱节。论文建议的标准化披露（tokens/solved、no-action turns、失败类别向量随模型名一并给出）本质上是把“脚手架配置”变成一等元数据，让比较在同等成本约束下进行。这与其说是否定某个模型，不如说是把评测从“模型秀”拉回“系统选型”。

## 工业界落地可行性评估
高度可行，且对编码 agent 选型与评测有直接指导意义。企业比较编程 agent 时必须固定或显式报告 harness，否则"谁更强"的结论不可比；其失败指纹分类（REASON/VERIFY/TIME 等）可用于落地时区分失败源于 harness 还是模型，从而指导监督策略——例如 Goose 卡住即诚实放弃（REASON 主导、零 VERIFY，意味着它不会在错误上硬撑），OpenCode 命中测试的解更可信但 idle spinning 多、需更多人工等待。论文同时提供 token/时延/监督负担等部署相关信号，适合编码 agent 供应商评估与上线前测试；配套已开源 harness 配置、原始 trial 日志、聚合快照与分析脚本（github.com/namanvats/scaffold-effects），便于复现与二次评估。对工程团队的实际建议是：不要只盯 pass rate，而应在给定 token/时延预算下选 harness–model pair，并把 token 用量、idle turns、失败类别随模型名一并披露，这样采购与内部评测才不会陷入"分数高但账单爆炸"的陷阱。局限在于该研究基于 Terminal-Bench Pro 命令行任务，是否适用于以 IDE 插件或 PR 自动化为主的软件工程场景，仍需另行验证。对工程团队，最实用的落地动作是把评估单位从“模型”改成“harness–model pair”，并在给定 token/时延预算下选型，而非盲信 pass rate。失败指纹可直接转化为监督策略：Goose 卡住即诚实放弃（零 VERIFY）意味着它的“成功”更可信、但需人补上验证；OpenCode 虽常命中测试却 idle spinning 严重，需要人盯着别让它空转烧钱；OpenHands-SDK 爱验证但易撞 MAX_TURNS，则应考虑放宽轮次上限。论文开源了 harness 配置、原始 Harbor trial 日志、聚合快照与分析脚本，使二次评估与复现门槛很低。需要提醒的边界是：本研究基于 Terminal-Bench Pro 的命令行任务，结论能否推广到以 IDE 插件、PR 自动化或长程仓库维护为主的软件工程场景仍待验证；且闭源商业产品（如各厂商托管 agent）未纳入，其脚手架行为可能与这三款开源 harness 迥异。总之，本文对“为什么我的 agent 账单和榜单对不上”给出了直接答案：先看 harness，再看模型。落到采购流程，建议在 RFP 或内部评测模板里固定 harness 规格（轮次上限、上下文预加载策略、重试逻辑），并把 token 预算与最大等待时间写进验收标准，否则供应商可用更费钱的脚手架刷高通过率。论文开源的 trial 日志还支持“失败指纹对照”：同一任务在两 harness 上分别 REASON 死和 TIME 死，能直接定位是模型不会做还是脚手架逼它空转，从而决定该换模型还是该换框架。这种把“为什么失败”显性化的能力，是 paper 对工程实践最实用的贡献之一。
