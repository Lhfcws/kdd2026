# Evaluating Governed LLM-Driven ML Experimentation: Lifecycle, Provenance, and Failure Metrics

## 背景与 Idea
自主机器学习实验智能体（autonomous ML experimentation agent）能自动提出代码改动、跑训练并报告指标提升，但它往往只展示"最终任务分数"，不展示这些动作是否受边界约束、是否可审计、是否可复现。论文指出，一个更高的验证 AUC 并不能回答一连串过程性问题：智能体是否只改动了被允许的文件？失败试验是否被保留而非静默丢弃？空操作（no-op）补丁是否被拒绝？保留/丢弃决定是由外部验证器做出还是模型自说自话？系统是否反复尝试已知会失败的想法？没有显式治理指标，这些属性都不可观测；而对科学 ML 而言，过程的可见性（observability）直接决定实验是否具备审计性——即每条决策及其证据是否可追溯、可复现。

论文建立在"Agent = 模型 + 工具外壳（harness）"的分解之上：模型负责提出动作，工具外壳提供执行边界、状态追踪与验证，两者共同组成一个复合 AI 系统。论文把治理责任从模型侧移到一个固定的"控制平面"（control plane），并把治理指标提升为一类一等公民的评估标准。它对比了若干相关系统以凸显定位差异：AIDE 是耦合的优化循环，搜索策略、评估器与方案摘要共享同一进程状态，用内存树节点存方案，没有外部追加式账本、没有挂起试验守卫、没有类型化失败分类，进程崩溃则中间方案不可恢复；MLAgentBench、MLE-bench、MLGym、FML-bench 等问的是"智能体在这项任务上是否提升了性能"，而本文问的是"无论结果如何，harness 是否保证每次试验都被约束、被分类、被来源追踪"；MLflow、Weights & Biases 等实验追踪器只在运行产生后记录结果，并不治理智能体循环，也不在训练前分类无效编辑尝试。本文因此把自己定位为一个治理层：任何基准任务都可通过 NodeSpec 契约被包进去，治理评估与任务指标结果解耦。

论文的核心问题不是"指标是否提升"，而是"智能体是否以受约束、可审计、可复现的方式行事"。它提出把六类治理指标（接受率、无效动作率、重复坏提议率、来源完整性、制品引用完整性、失败分类法）与任务指标并列报告，使过程行为在审计记录中可被检视。这一视角的现实根基是科学 ML 的可复现性危机：当智能体自动提出成百上千次改动时，若只保留"最终分数"，则任何一次有问题的中间决策（如越权改了数据划分、或重复尝试已知失败的想法）都无法在事后被追溯或反驳，而审计性（auditability）正是连接"实验做了什么"与"结论能否被相信"的桥梁。

## 核心方法
论文实例化了一个"受治理的控制平面 harness"，由三类可替换组件与一个固定契约构成。manager（提议者）每次提出一个受约束的变更（摘要、理由、目标参数、预期效果）；worker（执行者）把补丁与运行制品物化；control plane（控制平面）拥有权威：作用域校验、生命周期执行、指标解析、保留/丢弃决策、内存更新与追加式账本记录，且这些权力从不委托回智能体。这正是"替换原则"：无论 baseline 启发式、prompt_manager、LangGraphManager 还是 AIDE 式树搜索，任何 manager 后端都可替换而不改变治理契约；LocalWorker 与 ClawWorker 两种 worker 实现覆盖不同的可复现光谱。

控制平面的核心是一个追加式账本（append-only ledger），采用 JSONL 格式、永不被覆盖或删除。每条试验在被允许开启下一个预算槽之前，必须向账本追加恰好一条不可变记录，包含：提议文本、补丁引用与哈希、原始日志引用、解析后的指标、有效性状态、决策、失败类别（若有）、五个来源 ID 与可复现性哈希。为让审计性可操作，论文用五个期望属性（desiderata）来定义最低可检视条件：D1 受约束的编辑作用域（智能体不能改受保护的基准/数据/评估文件）、D2 完整的尝试记账（包括无效提议与崩溃在内的每次尝试都被记录）、D3 独立裁决（接受或拒绝由固定控制平面规则决定，而非模型）、D4 来源关联（每条记录链接到补丁、配置、运行、指标与决策证据）、D5 可重算性（无需重跑训练即可从账本重算聚合治理声明）。

试验生命周期用一个状态机强制：每个试验从 pending 进入 executing，最终落到恰好一个终态——kept（保留）、discarded（丢弃）或 failed_invalid（失败—无效）。控制平面在 worker 执行前写入一个 pending guard 文件，执行正常则终态转换时删除；若进程中途崩溃，guard 文件留存，下次活动启动时触发 PendingTrialError，通过 recover_pending.py 检视陈旧 guard 并补一条 failed_invalid 记录，从而杜绝"静默完成"或"悬挂试验"。作用域校验器在训练开始前把补丁与 NodeSpec 白名单比对：触碰冻结文件的补丁被拒绝、记录且阻止其污染节点状态。论文强调来源完整性（provenance completeness）是结构性不变量（structural invariant），由控制平面代码构造保证，而非实验期间"恰好没崩溃"；1,445 次试验观测到的 100% 完整性只是它的经验证明。

为验证该契约跨任务是否成立，论文在六个基准节点（node）上跑同一套控制平面，唯一逐节点差异是 NodeSpec YAML（可编辑路径、冻结路径、运行命令、指标解析器、预算范围）。六个节点分别是：resnet_trigger（波形分类，val_auc，作为主科学案例与内存消融基底）、lr_synthetic（纯 NumPy 逻辑回归，无依赖、跨节点迁移校验）、openml_credit_g 与 openml_bank_marketing（公开 OpenML 表格分类，治理迁移基底）、mlagentbench_vec（NumPy 卷积加速任务，基准兼容探针）、autoresearch_linux（GPT 预训练，val_bpb，最小化方向，作为高失败率真实任务压力案例）。提议者统一用 deepseek-v4-flash（经 LangGraph）以固定模型、降低跨节点能力混淆；论文明确区分"模型无关发现"（来源完整性、生命周期正确、作用域执行）与"可能 manager 特定的提议质量发现"。

论文定义了六类治理指标（表 5）：接受率 AR=|kept|/N，反映有效改进编辑占比；无效动作率 IR=|failed_invalid|/N，反映不可评估试验；重复坏提议率 RBR=重复坏提议/N，刻画智能体是否反复提相同失败编辑；来源完整性=五个 ID 齐备的试验/N；制品引用覆盖率=物化运行的补丁/日志引用与哈希、以及运行前失败的已分类记录；失败分类法=各 FailureCategory 的计数。失败分类由控制平面在写账本的终态转换时贴标签（而非事后由 manager 贴），主证据集出现的五类是 invalid_edit_scope、no_op_patch、proposal_precondition_failed、runtime_error、node-level invalid_config；模式还支持 metric_missing 与 edit_failed，但二者未出现在主 1,445 试验证据中。有效的非改进被标为 discarded（内部 degraded_metric），而非 failed_invalid。这种把失败标签写在账本终态转换时（而非事后由 manager 贴）的设计很关键：它保证了分类由固定控制平面规则决定，不被提议者的自我叙述影响，从而让 RBR、IR 等指标成为对"智能体实际行为"而非"智能体自称行为"的测量；同时把 non-improving 标为 discarded 而非 failed_invalid，区分了"无效编辑"与"有效但无效"两类性质不同的结果。

内存消融作为一个诊断探针而非性能主张：内存接口三种模式——无先前试验上下文、追加式摘要、带理由增强的摘要——用于检验 manager 在看到先前受治理结果后行为是否改变，以及 RBR 能否探测这种行为改变。预声明假设是 RBR(none) > RBR(summary) > RBR(rationale)，即带理由的记忆比原始摘要更能减少重复坏提议。对照实验用一对匹配的无治理反事实（ungoverned counterfactual）来量化治理的净收益：在没有控制平面时，50 个试验中 43 个（86%）不留下任何账本记录，且一次全面失败的活动的与"从未运行过的活动"无法区分。

## Performance 概括
在 1,445 个受治理试验上，六个生命周期节点的 provenance completeness 均达到 100%，且该不变量由构造保证、跨任务类型、worker 类别与失败机制（包括 autoresearch_linux 的 120 次全失败臂与协议污染案例）均成立。对照的 ungoverned 反事实中，86%（43/50）完全没有账本记录，几乎不可审计；一次全失败活动与从未运行的活动无法区分。真实 worker 科学节点案例（resnet_trigger，20 次试验）记到 4 kept / 5 discarded / 11 failed_invalid，AR 0.20、IR 0.55、provenance 与决策记录完整性均为 100%；其 val_auc 从 0.7747 升到 0.7827（+0.008022），落在基线种子噪声区间内，被论文当作"循环正确运行"的次要证据而非优化主张。内存消融显示：摘要上下文能降低 ResNet-trigger 上的重复坏提议率，但不迁移到合成节点；autoresearch_linux 的无内存臂在该特定任务/接口配置下产生 100% runtime_error 失败，但全部 240 次试验仍被完整分类，说明控制平面治理独立于失败原因。结构重标一致性（Cohen's κ）在 50 个分层抽样上达 0.830。

## 论文价值与不足
价值在于把"治理指标"确立为自主 ML 实验系统的一等评估标准，并给出一个可实例化、可跨节点复用、可仅从账本重算的 harness：来源完整性、生命周期正确性与作用域执行是模型无关的结构性保证，对 autoML/AI 实验审计、合规与科研可复现性有直接现实意义；它用匹配的 ungoverned 反事实清晰量化了"治理到底买到了什么"。不足在于：实验规模（1,445 试验）与所用模型范围有限（提议者基本固定为 deepseek-v4-flash，仅少数节点换 qwen2.5-coder），跨模型泛化与大规模结论未充分验证；governed 与 ungoverned 的对比存在配置差异（是否仅由治理本身造成）带来的因果性干扰，论文坦承其结构重标一致性检查并非人工评测者间研究，完整人工 inter-rater 验证留作未来工作；内存消融被明确限定为诊断探针，不构成"某记忆格式普遍更优"的结论。另一个治理含义是：来源完整性作为结构性不变量，意味着它不依赖任务难度或失败率——即便在 autoresearch_linux 的 120 次全失败臂与协议污染案例中仍为 100%，因此它对高失败率但仍需可审计的真实科研场景尤为可贵；相比之下传统追踪器（MLflow、W&B）只在运行产生后记录，无法在训练前就拦截越权编辑或分类无效尝试。

## 工业界落地可行性评估
落地场景明确且与现有工程实践契合度高：企业内部 autoML/实验平台（如基于 MLflow、W&B 的流水线）可在外层包一层"控制平面 + 追加式账本"，把实验过程变为可复现、可追责、可重算的记录，从而满足模型风险治理与审计合规（如 AI 可审计性、实验留痕）的诉求。整体可行性较高，属于"监管理念 + 轻量工程"的可直接复用方案：NodeSpec 白名单、pending guard、状态机与 JSONL 账本都不依赖特定模型，manager/worker 可替换，且治理指标无需 GPU 即可从账本重算验证。落地前需注意三点：一是控制平面会引入额外延迟与少量工程成本（每试验一次账本写入与作用域校验），对高频小试验需评估开销；二是 keep/discard 决策规则（如"仅当指标优于当前最佳才保留"）需按业务设定，否则可能错误丢弃有效探索；三是该方法聚焦过程治理而非最终性能优化，宜作为审计与合规层叠加在既有 autoML 之上，而非替代搜索策略本身。从合规视角看，论文的"模型无关发现"（来源完整性、生命周期正确、作用域执行）恰对应模型风险治理中对"决策可追溯、过程可复现"的硬要求，因此该控制平面可作为 autoML 平台满足审计留痕诉求的现成蓝图；不过需结合企业自身的实验管理栈评估 pending guard 与账本写入的吞吐影响，并在 keep/discard 规则上明确业务判据（如是否允许"探索性保留"而非仅保留当前最优），否则可能过早丢弃仍有信息价值的失败试验。
