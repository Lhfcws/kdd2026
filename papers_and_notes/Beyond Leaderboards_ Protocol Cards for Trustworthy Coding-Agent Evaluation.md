# Beyond Leaderboards: Protocol Cards for Trustworthy Coding-Agent Evaluation

## 背景与 Idea
coding-agent（代码智能体）在仓库级软件工程里被当作"复合系统"而非孤立模型调用来评测：在仓库级设定中，agent 要检索文件、审查 PR、生成补丁、调用工具、参与迭代修复循环。一个上报分数可能取决于展示给 agent 的任务证据、生成或修订输出的工作流、生成后的检查、打分的指标，以及计算成本的口径。这意味着榜单分数看似是"模型内在能力"，实则部分由上下文构造、编排、验证、度量与成本核算等隐藏选择所产生。论文（Keqin Zhang，CUHK 深圳；Sharon Lee，剑桥；KDD 2026 Workshop）指出，评测协议（protocol，即决定 agent 看到什么信息、如何产出与检查输出、如何度量成功与核算成本的一整套设定）本身是一个隐藏变量，忽略它会导致不可复现、不可比的结论。作者因此提出 Protocol Cards：把分数与其产生条件一起记录，让评测过程可复现、可审计，而不是只报告一个数字。其动机问题很直接——"当一个 coding-agent 被报出某分数时，必须披露哪些协议信息，该分数才可被解释、可复现、可信？"相关工作已有一系列评测文档化框架（BenchmarkCards 记录基准级属性与局限，EvalCards/Evaluation Cards 提供评测与运行级元数据模式，Claw-SWE-Bench 进一步显示提示、工作区构造、运行时预算、补丁抽取与评测器配置共同构成"有效基准契约"），本文更窄也更实证：不主张"分数需元数据"是新发现，而是指出 coding-agent 专属的协议分解并给出受控实证。

## 核心方法
论文把 coding-agent 的评测条件组织为三个维度加一组横切元数据。信息协议（Information protocol）记录 agent 能访问什么证据：数据集/版本、任务选择、上下文与 oracle 访问、检索、打包、token 预算。过程协议（Procedure protocol）记录输出如何被产出与检查：工作流、工具、环境、修订策略、验证深度、重试与失败处理。度量协议（Measurement protocol）记录输出如何变成分数：指标、匹配器/评判器（matcher/judge，匹配器按确定性规则比对，评判器用 LLM 判定语义等价）、人工审计、聚合、不确定性、成本核算。横切运行元数据（cross-cutting run metadata）则要求披露模型与供应商版本、提示模板、解码设置、种子、重试与失败策略、执行日期与环境版本——这些是一等披露字段，不因三维度存在而被省略。

论文把"验证"与"精炼"明确拆成两种操作，这是协议卡的关键设计。验证（verification）对一个已生成的输出打分、过滤、标记或升级，但不修改最终答案；精炼（refinement）把草稿或反馈返还生成器，允许修订答案。二者必须分开报告，因为前者只改变"如何检查答案"，后者会改变"生成的答案本身"。举例：验证器可判断一条审查发现是否准确定位了 CacheManager.get() 中的未加锁读写路径，但不能改写该发现；而 self-refine 工作流可把含糊的"可能存在并发问题"替换成具体的读写竞争解释。验证深度用 V0–V3 四级表示：V0 无检查；V1 加 TestVerifier（要求预测与参考发现共享至少一个规范化源文件路径或基名）；V2 再加 StaticCheckVerifier（拒绝命中已知误报集的发现）；V3 再加 CriticVerifier（用确定性 oracle 检查，要求非空预测是参考发现的精确子集）。这些检查都是局部、确定性的，不引入额外 LLM 调用，也不修订最终候选。

度量层的核心指标是文件级信噪比 SNRfile：在匹配族 m 下，Mm 为匹配到真实问题（ground-truth concern）的发现集合，Um 为未匹配发现，SNRfile = |Mm| / (|Mm| + |Um|)。举例，若 agent 产生 5 条发现，其中 2 条定位到相关文件、3 条未匹配/含糊/无关，则 SNRfile = 2/(2+3) = 0.40——它奖励精准定位、惩罚多余未匹配，但刻意保守，只衡量文件级定位而非完整语义正确性。与之互补的是 bug-hit rate（BHR，是否至少找到一个真实问题）：一个模型可 BHR 高但 SNR 低（找到一个真问题却产出大量无关发现），或 BHR 中等但 SNR 较高（产出少而精的发现）。论文刻意把 SNRfile 作为可复现的头部指标，而把基于语义评判器（如 DeepSeek V3 judge）的打分仅作校验层，因为评判器本身有提示、位置、风格、打分等偏差，不可直接当作真值。

实证基于两类主研究与两项诊断。E1 代码审查审计，固定 200 个任务 × 4 个验证深度 × 3 种上下文体制 × 3 种工作流 = 7,200 条记录；E2 oracle-file 条件补丁构造，取 150 个 SWE-bench Lite 实例（至少含一个 FAIL_TO_PASS 测试），仅在"相关文件已被 oracle 定位"前提下序列化三种上下文，得 1,350 条记录；E3 成本核算敏感性，复用 E1 输出只改成本聚合规则。上下文体制分 diff-only（仅补丁差异）、structured（结构化上下文）、full-raw（完整原始上下文）三档。统计上用任务级 bootstrap（10,000 次重采样、固定种子）算 95% 置信区间与配对 p 值，且只在共享同一任务身份的协议条件间对比，以控制任务难度带来的方差。E2 本质上估计的是 P(clean apply | 相关文件已正确识别)，而非端到端"agent 独立定位文件+构造语义正确补丁+通过可执行测试"的概率，因此不解释为官方 SWE-bench 解决率。

正是这种"条件概率"视角解释了为何 diff-only 失败率高达 92%：在 SWE-bench 式补丁中，输出必须给出精确的仓库相对文件路径，而 diff-only 上下文下模型即使想对了逻辑改动，也可能生成部分路径、漏掉前缀约定、或把编辑放进补丁上下文里不存在的文件，导致补丁无法干净应用；structured 上下文通过暴露文件级锚点缓解了这一失败。这同时说明协议卡的粒度要细到"文件路径序列化方式"这种看似琐碎、却决定 8%→50% 成败的细节。论文在统计上还强调单位分析（unit of analysis）是"固定任务、上下文体制、工作流、验证深度下的生成记录"，并用任务级 bootstrap（10,000 次、固定种子）算置信区间与配对 p 值，只对共享同一任务身份的协议条件做对比，以剥离任务难度方差——这种严谨设计是其结论可信的基础，也暗示协议卡应附带随机种子与重采样配置以便他人复现。

## Performance 概括
从 diff-only 升级到 full-raw 协议，ΔSNRfile = 0.007（p = 0.002），95% CI [+0.003, +0.012]，信噪比统计显著但绝对幅度小；跨供应商/模型稳健切片方向一致（Δ = +0.019，p < 0.001）。验证深度 V0→V3 在 E1 下 ΔSNRfile = +0.003（p = 0.330）不显著；验证流水线相对单 agent 生成仅 +0.005（p = 0.037）。clean-apply rate（补丁能否干净应用到代码库）随协议完整度提高：diff-only 仅 8.0%，structured 提升到 50.4%，full-raw 进一步到 54.7%；但 E2 是 oracle 文件条件下的"可应用性桥接"，不是官方 SWE-bench 解决率。语义评判器（DeepSeek V3）把更多发现标为匹配：聚合 SNR 0.093 vs 0.087、BHR 0.440 vs 0.365，但因子级显著性随之改变（上下文在文件匹配器下显著、在评判器下不显著，工作流则相反）。成本口径反转了两种多调用工作流的排名：按总调用/接受输出，SA 5.68、SR 8.38、VP 10.82；按生成调用/接受输出，SA 2.27、VP 3.98、SR 4.79——即自精炼在总调用口径下更便宜，验证流水线在生成调用口径下更便宜，单 agent 在两种口径下都最便宜。

## 论文价值与不足
价值在于揭示"评测协议"是 coding-agent 评测中被忽视的隐藏变量，并用受控实证量化了上下文、工作流、验证、度量、成本核算各自的影响方向与显著性（核心结论以 R1–R4 四个 measured findings 组织），最终给出可操作的协议规范（Protocol Cards，含核心披露字段表）。它建立在 BenchmarkCards、EvalCards、Evaluation Cards 等评测文档化工作之上，但把披露结构做了 coding-agent 专属的分解（信息/过程/度量三维度），并明确区分验证与精炼。协议卡有三种实用场景：比较不同上下文体制/验证策略下的榜单结果（full-raw 下的高分不能与 diff-only 下的同等解读）、诊断改进为何在换匹配器/评判器/成本口径后消失、以及通过显式任务打包与成本假设支撑可复现。不足在于：其一，SNRfile 仅衡量文件级定位而非语义正确性；其二，E1 用确定性任务切片提升可复现性，却可能引入顺序偏置，跨供应商切片只是稳健性检查而非随机验证集；其三，E2 是 oracle 文件、补丁级，排除了检索失败、不跑可执行测试，不能估价端到端 SWE-bench 解决率；其四，结构化与 full-raw 上下文在顺序、冗余、格式、长度上也可能不同，无法把效应纯归因于信息量；其五，人类审计为单标注者、属诊断性而非总体级验证；其六，语义评判器是测量模型而非真值。clean-apply 的提升在 structured→full-raw 阶段已趋饱和（50.4%→54.7%），边际收益递减，且规范化协议本身需要额外标注成本。

## 工业界落地可行性评估
可直接落地：企业可在内部 coding-agent 评测中强制要求 Protocol Cards，统一协议描述，提升跨团队、跨时间结果的可比性与可信度，属于低成本、高杠杆的工程规范改进。建议把三维度与横切元数据写入评测报告模板，尤其披露上下文体制（diff-only/structured/full-raw）、验证深度、匹配器与成本口径——否则不同团队报出的 pass@1、resolved rate、clean-apply rate 不可直接比较，且 SWE-bench 类分数会因上下文序列化差异而大幅波动（diff-only 仅 8% 可应用，full-raw 达 54.7%）。落地障碍主要有二：一是编写与维护协议卡需额外标注与流程成本，且论文坦言字段集的"人类可用性"与"撰写成本"尚待验证；二是成本口径目前只用调用次数作代理，未纳入 token、供应商定价、缓存、并行延迟等真实经济成本，工业落地需自行补充完整成本模型。总体而言，它不改变评分指标，而是给指标加一层审计外壳，性价比高。值得补充的是，本文呼应了 harness 工程（harness engineering）一脉的研究：Meta-Harness 等工作表明 LLM 系统表现不只取决于模型权重，还取决于控制上下文构造、检索、记忆与编排的外部代码与工作流结构。本文的立场是——既然 harness/工作流层面的选择会实质改变分数，那么这些选择就不应被隐藏在"模型能力"的标签下，而必须作为协议卡的一等字段被披露与审计。因此协议卡与"优化 harness 提升性能"并不冲突：前者是让性能可被解释，后者是在已披露的条件下追求性能。对企业而言，最务实的落地是把协议卡接进现有评测 CI——每次跑 coding-agent 基准时强制产出一张卡，记录上下文体制、验证深度、匹配器与成本口径，并把不同团队的卡放进同一看板对比；只有当协议一致时，榜单数字才具有横向可比性，否则高一分可能只是因为用了 full-raw 上下文或不同的成本计数方式。

还需提醒，论文的结论是"协议敏感"而非"某协议全局最优"：它并未证明 full-raw 永远胜过 diff-only、也未证明验证深度越高越好（V0→V3 在 E1 下不显著），更未证明验证普遍无效——只是所测的深度检查在 E1 的确定性文件级指标上未可靠改善。因此协议卡的价值不在替你选协议，而在强制你"说清用了什么协议"，让结论可归因。对已经在跑 SWE-bench 类内部基准的团队，最直接的第一步是把上下文体制从默认的 diff-only 升级到 structured/full-raw 并记录，因为论文显示这能把补丁可应用率从 8% 拉到 50% 以上，而代价仅是序列化更完整的文件上下文——这是投入产出比极高、且完全契合协议卡精神的改动。
