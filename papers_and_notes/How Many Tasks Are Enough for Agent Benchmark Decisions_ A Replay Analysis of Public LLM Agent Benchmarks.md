# How Many Tasks Are Enough for Agent Benchmark Decisions? A Replay Analysis of Public LLM Agent Benchmarks

## 背景与 Idea
agent benchmark（智能体基准）的常规做法是在跑完全部任务后比较两个系统，但 agent 任务往往昂贵、异构、且与下游决策绑定，因此只跑一部分任务的"部分评估"非常诱人。本文作者 Wei-Jung Huang（独立研究者）指出一个被忽视的关键点：报告"我跑了百分之多少的任务"这个数字本身，并不能说明这次部分运行是否支持与完整 benchmark 相同的成对结论。这里需要先厘清 benchmark 里"系统"指什么——在本文语境下，一个 system 就是一条公开的 leaderboard 条目，它包含模型、提示词、工具、脚手架、重试逻辑等所有共同产出任务成败的组件。一旦全部任务跑完，benchmark 给每个系统一个成功率；对一对系统，使用者会问：系统 A 的成对成功率是否高到足以在当下决策中优先选 A。

作者区分了"运行更少任务"的两种目标。第一种是分数估计（score estimation）：用一小部分样本去估计完整 benchmark 的成功率，这类问题已有 HELM、Cer-Eval、FAQ 等工具覆盖。本文研究的是第二种、且更被忽视的目标：决策（decision）。也就是说，如果完整 benchmark 的结论是"A 比 B 好"，那么部分运行在给定误差目标、覆盖规则、以及"允许不给出结论"的上限之下，能否支持同一个结论？分数是一种测量，成对结论是一种决策，二者目标不同。

论文的核心概念是"最小充分任务预算（minimum sufficient task budget）"——在给定改进阈值、任务组覆盖规则、以及未解决比较上限之下，能可靠复现完整基准成对决策的最小任务比例。作者特别区分了"未解决比较（unresolved comparison）"，技术记号中称为 defer：当预算耗尽、且已观测任务不足以支持任何最终结论时，部分运行应当主动"保留结论"而非强行下判断。这种 deferral 机制正是部分评估区别于普通分数估计的要害，因为一份低误差的报告可能只是因为只决断了容易比较、而把困难比较全都 defer 了。

本文想回答的"失败模式"有三：其一，部分分数可能接近最终分数，却漏掉了会改变成对结论的任务组；其二，一个低误差规则可能只是因为它只对简单比较下结论、把难的比较都 defer 了；其三，cheap-first（先跑便宜任务）的排序可以省成本，却观测了与目标对子无关的任务组。这些都属于"决策失败"而非"估计误差"。

论文用一个小例子把问题讲具体：假设一次部分运行只观测了某一个 repository 里的任务，而在这个 repository 上 A 胜过 B；但如果未被观测的其余 repository 强烈偏向 B，完整 benchmark 可能得出相反的成对结论。一份只写"我跑了百分之多少任务"或"部分分数多少"的报告，完全不会说明已观测任务是否覆盖了比较所需的任务组。同样的逻辑也出现在"规则 withholding 大量困难比较"的情形：它的报告误差率可能很低，仅仅因为许多难题从未得到部分结论。论文因此明确：分析对象是已完成 benchmark 记录的"重放"——任务集、系统、任务结果都固定，变化的只是预算耗尽前观察到了哪些任务；目标是完整 benchmark 在固定记录下诱导出的决策，而不是对未来任务、总体抽样或正式在线停止的推断（后者需要不同的模型）。

## 核心方法
方法的主干是"重放（replay）"已完成的公开任务级记录：以 SWE-bench、AppWorld、tau-bench 三个公开基准中已跑完的系统与任务成败记录为固定输入，任务集合、系统、任务结果三者都不变，唯一变化的是"在预算耗尽前观察到了哪些任务"。也就是说，作者通过排列已完成记录的揭示顺序（reveal order），在固定记录上模拟大量部分运行，从而研究"观察到多少任务才能让部分结论匹配完整基准的结论"。需要强调的是，这种 replay 结论只描述那些已完成的记录，并不估计未来任务或总体层面的表现，因此目标比分数估计和在线停止（online stopping）更窄。

一个"充分预算"必须同时满足三个目标。第一是决策误差目标：条件 false-accept（当完整基准对 A 是负结论时，部分策略却给出正结论）与条件 false-reject（当完整基准对 A 是正结论时，部分策略却给出负结论）都要 ≤ 5%。注意这两个分母是"以完整基准决策类别为条件"的，未解决的比较仍留在分母里、既不算误接受也不算正确拒绝，这防止了策略靠"少下结论"来虚降误差。第二是任务组覆盖目标（coverage failure ≤ 5%）：覆盖规则要求每组任务都按其在完整集合中的比例出现，组的定义来自各来源可获得的元数据——SWE-bench 按 repository（代码仓库），AppWorld 按 difficulty（难度分层），tau-bench 按 domain（业务域，如 airline/retail/telecom）。具体所需数量 r_g(b)=max{1, min{n_g, floor(k_b·n_g/N)}}，即每组的下限大致等于该组在固定任务集里的占比；slack 版则每组再减一个任务，用来测试比例要求对预算的影响。第三是未解决比较率目标：defer(预算) ≤ 25%，即最多 25% 的比较在预算内仍无结论。论文默认 α=0.05、γ=0.05、η=0.25，但强调使用方应在 replay 前按自身风险与成本设好这些阈值。

改进阈值（threshold δ）是另一关键旋钮。0 pp 阈值只测方向：A 的成对成功率是否严格高于 B；5 pp 或 10 pp 则要求更大的超额边际才偏好 A。阈值本身改变了完整基准要复现的决策，因此论文在 0/5/10 pp 下都做了扫描。论文在 5 个百分点（5 pp）的预算网格上从 5% 扫到 95%，以观察预算逐步增加时各项指标如何达标。

策略层面，replay 对比了多种任务选择与决策规则，代表实际评估中常见的做法：uniform forced（随机抽任务、不考虑组或成本，且强制下结论）、group-stratified forced（按组分层展开揭示顺序）、cost-aware forced（仅在有成本字段时按被测系统成本升序揭示，用于测试 cheap-first 失败模式）、以及 coverage-aware bootstrap（主要策略，可在证据接近阈值时主动 defer）。bootstrap 策略用配对二值结果做重采样，只有当多数重采样都落在阈值同侧时才下最终结论，否则保留；其可调参数 a（主用 0.05）是策略自身的调参，与 replay 层面的误差目标 α 数值相同但角色不同。此外还有若干对照策略：coverage paired-normal test、coverage exact McNemar test（仅在 0 pp 适用）、Neyman 分配（用已完成记录的组方差做分层抽样以估计"若知道方差能省多少预算"）、Serfling 有限总体半径等，用来分离"是分配方式、是不确定度、还是 bootstrap 决策规则在驱动预算"。

敏感性检查覆盖：bootstrap 截断值 a∈{0.02,0.05,0.10}、重采样次数（100/200/500）、揭示顺序的随机种子区间、配对方向（保持每对无序系统只用一个方向作为依赖性检查）以及经典配对检验。复现包公开在 GitHub，含 replay 代码、schema、固定种子、衍生表格与各类检查脚本。实验配置上，SWE-bench 与 AppWorld 每对有序比较用 500 个揭示顺序、200 次 bootstrap；tau-bench 用 2000 个揭示顺序、500 次 bootstrap。涉及的记录规模：SWE-bench Lite 552 个有序比较（276 个无序系统对），Verified 156 个有序比较（78 对），AppWorld 585 个任务、306 个有序比较，tau-bench 公开网格 12 个有序比较（6 对）、278 个 domain-task 项。

三个公开来源各自承担不同证据角色，理解这一点有助于读懂结果为何差异巨大。SWE-bench Lite 与 Verified 提供大量公开 leaderboard 条目的任务级软件修复成败（Lite 是"任务数很大"的案例，Verified 是"低重放误差仍留过多未解决比较"的案例），二者都按 repository 分组、无成本字段，故只做任务数 replay。AppWorld 解包了 36 个公开 leaderboard bundle（每系统两个 split），用官方工具解析出 585 个任务键、306 个有序比较，它测试"同样的局部预算问题是否出现在软件修复之外"、且提供稳定任务 ID、难度标签与场景 ID。tau-bench 公开轨迹网格选用 4 个 leaderboard 条目、12 个有序比较、278 个 domain-task 项，覆盖 airline/retail/telecom 三域（banking-knowledge 因检索配置不一致被排除），它自带成本与奖励处理字段，专门用来测试 cheap-first 失败模式——即按被测系统成本升序揭示时，部分运行是否仍覆盖了完成基准决策所需的域。所有这些 reveal 策略都在观测当前局部效应之前就固定了任务顺序，覆盖实际评估者可能做的选择：跑随机子集、强制任务组覆盖、优先便宜任务、要求重采样证据、或同时要求重采样证据与任务组覆盖；把它们对比起来，才能把单个聚合分数所掩盖的"错误决策、未解决比较、任务覆盖、成本"四类效应分离开。

## Performance 概括
在 0 pp、5% 预算网格上：AppWorld 首次达标于 15%，tau-bench 25%，SWE-bench Verified 90%；SWE-bench Lite 在 95% 前均未达标（primary coverage rule 下）。原因：SWE-bench Lite 在 0 pp 时即便误差/覆盖达标，仍有 55.92%（25% 预算）至 27.25%（95% 预算）比较未解决；SWE-bench Verified 在 25% 预算时误差与覆盖已达标，但 93.64% 比较未解决，直到 90% 预算才将未解决率压到 24.22%。提高阈值会改变结论：SWE-bench Lite 在 5 pp 达标于 55%、10 pp 于 35%，slack 覆盖规则下 0 pp 在 75% 才达标。tau-bench 的 cheap-first 排序省成本（仅用 11.51% 测试成本）却 100% 覆盖失败并给出错误成对结论（在 4/5 个 5 pp 正例与 2/2 个 10 pp 正例中产生 false-reject）。三个失败模式被坐实：uniform forced 在 25% 预算下对 SWE-bench Lite 与 AppWorld 的覆盖失败率高达 99.96%；cost-aware forced 在 tau-bench 仅用 11.51% 成本却 100% 覆盖失败；SWE-bench Verified 的低重放误差来自大量未解决比较而非真可靠。

## 论文价值与不足
价值在于首次把"部分评估报告"的失败模式系统化：它指出一个任务比例或局部分数会隐藏错误决策、漏掉任务组、或留下过多未解决比较，并给出可操作的"最小充分预算"概念与一整套重放方法论。论文的三点贡献（识别报告失败、定义最小充分预算、在公开记录上度量该量）对 benchmark 使用方、采购方、部署决策者都有直接指导意义，且公开了代码、schema、固定种子与衍生表格，可复现性强。一个重要的使用原则是：部分评估必须显式声明改进阈值、任务选择方式、覆盖规则、决策规则与未解决比较数；当这些目标未达成时，正确输出是"跑更多评测"或"不下部分结论"，而不是强行给一个数。

不足也清晰。第一，方法只基于已完成记录的排列重放，因此只描述那些固定记录上的决策行为，并不估计未来任务或总体层面的性能——要把结论推广到未来任务抽取，需要额外的抽样模型。第二，分组依赖公开元数据（repository/难度/domain），没有涵盖语义聚类或失败模式聚类；作者承认当任务文本、embedding 或失败标注可用时，学习到的语义分组可能更有用，但那会改变覆盖规则、需作为另一个策略变量评估。第三，replay 只测试了 random / stratified / cost-ordered / coverage-aware 这类在观测当前局部效应之前就固定顺序的策略；自适应（sequential testing）或主动任务选择（active selection）可能改变预算——Neyman 对照显示方差感知的分配能降低预算，但实时策略需要先验或历史方差估计。第四，证据覆盖的 agent 场景有限：SWE-bench（软件修复）、AppWorld（交互式编码与 App 操作）、tau-bench（工具-agent-用户交互），且都只限已解析的任务级多系统记录；要推广到 OSWorld、WebArena、AgentDojo、Terminal-Bench 等需要这些基准的解析任务级记录。

## 工业界落地可行性评估
这篇论文直接服务于所有需要"用更少评测钱做系统选型"的团队，落地可行性高、且几乎零模型依赖——它是一套评估规范与开源重放工具，而非需要训练的新模型。对采购/部署决策者而言，论文建议的"声明阈值 + 覆盖规则 + 决策规则 + 未解决比较数"的报告范式，可以显著降低 benchmark 成本同时保住结论可信度：例如 SWE-bench Lite 这种大任务数案例若只用分数估计会遗漏大量未解决比较，而按本文协议跑 replays 能告诉你真实需要的预算。它特别适合 leaderboard 预筛（把未解决的对子直接送回完整 benchmark）和部署前的成对决策审计。落地障碍主要有三：其一，trials 的分组元数据（仓库、难度、域）必须可得，否则覆盖规则无从定义，这要求企业内部 benchmark 也保留结构化任务元数据；其二，阈值 α/γ/η 需由使用方按风险与成本自行设定，不能照搬论文的 0.05/0.05/0.25；其三，自适应或方差感知的任务分配虽能进一步省预算，但需要历史或试点方差，不是开箱即用的。总体看，作为评估规范与可复用工具链，它在工业界的采用门槛低、收益明确。
