# MacCode Lab: A Reproducible Single-Machine Harness for Execution-Guided Code Agents, and When Repair Actually Helps

## 背景与 Idea
代码 agent 评估正从一次性 leaderboard 走向随模型、提示词和 agent 组件变更而反复执行的工程实践：模型提供商发版、提示词模板修订、工程团队改动 agent loop，都需要重新跑评测。这种"反复评估"体制强调与一次性榜单不同的性质——评估必须经济到能频繁跑、稳健到能无人值守跑、并且足够可观测以解释"分数为什么变了"而不只是报"变了"。因此论文认为，本地代码 agent 评估工作流本身是一个系统工件（systems artifact），而非一次模型调用：它要加载模型、管理基准数据、生成代码、安全执行、分类失败、尝试修复、持久化状态，并跑得足够久以暴露运行期故障模式。这些要求在当前 Apple Silicon 工作站上已可行——单台大统一内存机器能托管强开放权重模型、执行数千个候选程序而无需云集群，紧凑的稀疏激活混合专家（mixture-of-experts）模型让本地评估成为现实设置。论文提出 MacCode Lab，一个在单台 Apple Silicon 工作站上、基于 MLX 量化开放权重模型运行的执行引导式（execution-guided，即用测试执行反馈驱动生成与修复）代码 agent 评估框架，目标是把"评估一个代码 agent"本身当作可审计、可复现的系统工件来研究，而非简单地给模型打分。核心关切有两点：其一是执行引导式 repair（错误反馈驱动的修复循环）到底在什么时候真正有用；其二是仅以公开测试集（public tests）通过率来比较模型会产生多大偏差。这两点之所以重要，是因为近年基准（如整程序重建、上下文检索、技能注入、结构化动作空间）把注意力从“能否写出代码”转向“上下文管理、失败恢复与长程效率”，而本地评估能否如实反映这些能力，直接关系到工程团队是否会被一个虚高的 public-test 分数误导。把评测当“systems artifact”的判断有具体含义：一次本地评估要依次完成“加载模型→管理基准数据→生成代码→安全执行→分类失败→尝试修复→持久化状态”，并且要跑得足够久以暴露运行期故障（如子进程挂死、KV cache 撑爆）。Apple Silicon 的“统一内存”（unified memory）是关键使能技术——大模型权重与中间激活共享同一块高带宽内存，单机即可托管强开放权重模型并并发执行数千候选，而不必上云集群。这也解释了为何论文选稀疏激活的 MoE 模型：少量活跃参数让本地推理在有限算力下仍可接受，从而把“反复、经济的增量评估”从设想变为可操作设置。这也顺带解释了论文为何强调“resume-safe”：本地长跑可能因断电或进程被杀中断，若不能断点续跑就要从头再来，而把每任务记录、运行状态、bandit 状态都落盘，就能无人值守地跑完数百任务并在中途检视进度。

## 核心方法
MacCode Lab 是一个全本地、可断点续跑（resume-safe）的执行引导式评估 harness，控制回路为：task cache → difficulty-conditioned prompt bandit → local MLX model → typed execution against tests → failure classification → error-aware repair prompt → persist record / status / bandit state → 循环至预算耗尽。它摄取缓存的 LiveCodeBench v6 前 200 个任务与 HumanEval 全部 164 个任务，使用一个按难度条件化的 UCB1 bandit 在 8 种 prompt 风格中选择（8 风格为 direct / careful / structured / debugger / invariant / counterexample / template / pragmatic），风格选择非静态：bandit 按难度桶维护、为当前任务选 top-k 风格，且预算本身难度感知（简单任务更少初始风格与修复轮、困难任务更激进探索）；实验中 worker 还并行生成若干候选以同时利用 CPU 与 GPU。执行层按任务类型分发：stdin/stdout 类（Codeforces、AtCoder 风）作为程序运行并归一化比较输出；functional 类（LeetCode 风 LiveCodeBench）包成 harness 解析参数并比较返回值；call 类（HumanEval）追加数据集自带 check 函数断言；候选均在子进程超时内于临时目录运行，并预置公共 import 前缀以免因缺 import 受罚——当前仅覆盖单文件 Python 的这三种分发，仓库级/多文件/非 Python 不在范围内。在隔离子进程中运行候选程序后，框架把失败按 stderr/stdout 模式归类为一个紧凑 taxonomy（syntax / assertion / name / timeout / wrong-answer 等），并将错误特定的轻量提示送入 execution-guided repair loop：语法失败提示检查缩进与括号、名称错误提示检查符号定义、超时提示降低渐近复杂度、答错提示重读规范与边界。这些提示是有意轻量的反馈通道，而非手工求解器。关键设计是隐藏测试（hidden tests）仅用于事后重打分：运行期间 worker 只看到任务说明、起始代码与公开测试，隐藏用例以 base64+zlib 编码存于任务记录元数据，全协议分数在生成结束后才解码重放，绝不进入生成或 repair 提示，以避免污染。框架把每个任务的记录、运行状态与 bandit 状态持久化到磁盘（records.jsonl、status.json、summary.json、bandit.json 等），从而支持无人值守运行、运行中检视与运行后重打分；reproducibility appendix 还提供 reverify_all.py，从发布的运行记录独立重算每个计数、重跑公开测试、解码隐藏用例做全协议重打分，隐藏用例只作只读评分资源。8 种 prompt 风格并非装饰：direct 给最短正确解、careful 先推演边界、structured 显式处理、debugger 走测试驱动修复、invariant 锁定关键不变量、counterexample 先找反例、template 用辅助函数搭主路径、pragmatic 写稳健可本地验证的代码；bandit 在这些风格上按难度学习偏好，使“简单题少探索、难题多探索”，其学到的 per-difficulty 偏好可直接从持久化的 bandit.json 读出，成为“哪种提示对哪类题有效”的可解释证据。repair 提示刻意保持轻量，只在执行轨迹已暴露缺陷后才打开反馈通道，而不是提供手工求解器，这保证了修复增益来自“执行引导”而非“答案泄露”。隐藏测试以 base64+zlib 编码存于每条任务记录的元数据，重打分时解码执行且仅作只读评分，从机制上杜绝生成期看到答案。dispatcher 对三类任务的归一化比较（strip 行尾空白、比较返回值或断言）保证了评分口径与公共基准一致，而共享 import 前缀避免了“因缺 import 被误判”这种与模型能力无关的实现噪声。失败 taxonomy 把 stderr/stdout 模式映射到 syntax/assertion/name/timeout/wrong-answer，使“为什么挂”可视化，其中 syntax 失败以 562 次居首，明确指向“生成合法性”是本地小模型的首要瓶颈。

## Performance 概括
在 LiveCodeBench 上，repair 对 35B 模型将公开测试通过数从 89 提升到 113，但对 7B 模型没有净增益（公开测试 125→125，full protocol 下 repair 反而从 102 降到 99）。当用完整 hidden-test 协议重打所有被接受的解时，35B 仅丢失 3–7 个解（full protocol 从 88 升到 106），而 7B 丢失 23–26 个（102 与 99），即 public-to-hidden 衰减在两者间严重不对称。结果是：仅靠公开测试的比较偏向 7B，但在完整协议下差距收窄、且在 repair 条件下排序反转（106 vs 99）。HumanEval 因接近饱和，repair 对两模型最多只改变 1 题。Wilson 95% 置信区间约为 ±7 个百分点，作者明确不宣称跨模型排序具有统计显著性。失败 taxonomy 中 syntax 失败以 562 次居首，是明确的工程改进目标。实验中两个模型（Qwen3.6-35B-A3B 的 3-bit MLX 与 Qwen2.5-Coder-7B 的 4-bit MLX）均在 M5 Max 128GB 单机上以 greedy 解码（temperature 0）运行，repair 配置为 --initial-styles 3 --repair-rounds 2 --repair-beam 2。

## 论文价值与不足
论文的主要价值在于提供了一套可复现的本地评估仪器，并给出"repair 是否有用取决于具体模型而非仅取决于任务"的实测证据，以及 public-test 分数与 full-protocol 结果可能系统性分歧的警示。对工程实践有两点直接启示：其一，repair 不是普适利好，对近饱和的 HumanEval 基本中性、对小模型无净增益、只对较大的通用模型在 LiveCodeBench 上明显有益；其二，public-to-hidden 落差因模型而异，应读"落差"而非"公开分"。不足在于（论文以 Threats to Validity 列出）：研究仅覆盖两个模型、单一硬件/量化/MLX 版本，两模型在参数量、量化档与专精度上本就不同，故绝对分不是受控的规模研究，仅用于说明 repair 收益与 public-to-hidden 流失随模型变化；LiveCodeBench 用的是确定性前缀 200 题而非分层随机采样，结果为单 seed，且仅支持单文件 Python 任务；repair 同时改变了"错误提示反馈"与"额外采样次数"，未通过配对消融分离"错误提示、额外样本、bandit 状态"各自的因果贡献（两种条件各为独立运行，bandit 初始选择状态相关，连 greedy 下首试通过数也略有差异，如 35B 的 91 vs 89、7B 的 125 vs 119）；contamination 方面 LiveCodeBench 用发布窗口缓解，但无法完全排除模型见过部分任务。论文在 Threats to Validity 里把局限拆得很细，工程上最该记住三条：其一，两个模型在参数量、量化档、专精度上本就不同，所以绝对分不是受控的规模研究，只用于说明“repair 收益与 public-to-hidden 流失随模型变”这一评估性结论，而非给模型排名；其二，repair 同时改了“错误反馈”与“额外采样次数”，未做配对消融分离“错误提示、额外样本、bandit 状态”各自的因果贡献，因此只能说“完整 repair loop 在该设置下帮了一个模型”，拆成分量留作未来工作；其三，LiveCodeBench 用的是确定性前缀 200 题而非分层随机抽样，且结果单 seed，故 Wilson ±7pp 之外不能过度解读，尤其 HumanEval 仅 1 题差异不应被放大。这些限定的共同指向是：本文的贡献是“方法论与仪器”，不是“模型排行榜”，读者不应把 35B 与 7B 的绝对分当作规模结论，而该把注意力放在“repair 收益随模型变、public-to-hidden 落差随模型变”这一评估性发现上。

## 工业界落地可行性评估
单台 Apple Silicon 工作站即可作为可审计、可重放的代码 agent 评估工具，一个研究员可在一天内运行、检视并复现该评估（论文称 200 个 LiveCodeBench 任务配多风格 repair loop 数小时跑完），对经济频繁做增量评估的工程团队具有现实吸引力。论文明确建议：本地 harness 在报告执行类分数时，应把 public-test 结果与其后针对全协议的模型特定重打分一并给出，因为 public-only 评分会对不同系统引入不同偏差——这正是许多内部榜单"小模型看起来更香"的根源。其释放的 harness、冻结运行记录（records.jsonl、bandit.json、status.json、summary.json、accepted solutions）与重验证脚本（reverify_all.py）可直接支撑结构化编辑、上下文缓存和自适应 repair 策略的可复现实验。落地要点：评估应作为"过程可观测"的一等工件，每次模型或 agent loop 更新都重跑并对比 full-protocol 重打分，而非只看公开测试通过率；repair 收益需按所用模型实测，不能默认开启就有益。局限是它目前只覆盖单文件 Python，对仓库级多文件、非 Python 或需长程交互的工程智能体场景尚无覆盖，且绝对分数不可与不同 scaffold/解码设置下的排行榜直接比较。使用者应把它当本地校验仪，而非又一个榜单。对工程团队，最该采纳的动作是：每次模型或 agent loop 更新都重跑评估，并同时报 public-test 与 full-protocol 重打分，因为 public-only 会对不同系统引入不同偏差——这正是许多内部榜单“小模型看起来更香”的根源。repair 收益必须按所用模型实测，不能默认开启就有益：论文显示它对近饱和的 HumanEval 基本中性、对小模型无净增益、只对较大通用模型在 LiveCodeBench 上明显有益。其释放的 harness、冻结运行记录与 reverify_all.py 让“过程可观测”成为一等工件，可直接支撑结构化编辑、上下文缓存、自适应 repair 策略的可复现实验。对已有云评估栈的团队，MacCode Lab 的价值在于提供一套可在笔记本上复现的“对照基线”：当你怀疑某个云端榜单分数受 scaffold 或解码设置影响时，可用它在本地以相同 harness 重跑验证，而不必复刻整套云端基础设施。
